## Commands

No lint/format tooling is configured. Tests use pytest against an in-memory SQLite DB (see `tests/conftest.py`) — no live Postgres needed to run them.

```bash
# Install (editable) with dependencies, including the dev group (pytest, httpx)
pip install -e ".[dev]"

# Run the dev server
uvicorn app.main:app --reload

# Run the test suite
pytest
pytest tests/test_product_version_cross_org.py -v   # single file
pytest -k test_get_version_across_orgs_returns_404  # single test

# Alembic migrations (run from backend/, alembic.ini lives here)
alembic revision --autogenerate -m "description"
alembic upgrade head
alembic downgrade -1
```

Alembic's `autogenerate` needs a live Postgres connection (`DATABASE_URL`); migrations authored without one (as `product_versions`' was) are hand-written to match the `op.create_table`/`op.create_index` style Alembic itself produces — check the revision chain (`down_revision`) against the newest file in `migrations/versions/` before adding another one by hand.

Environment variables are loaded from `backend/.env` via `app/core/settings.py` (`Settings`, pydantic-settings). Key vars: `DATABASE_URL`, `SECRET_KEY`, `DEBUG`, `API_PREFIX`.

`python-jose[cryptography]`, `passlib[bcrypt]`, and `email-validator` (needed by `app/modules/auth` and pydantic's `EmailStr`) are declared in `pyproject.toml`'s `dependencies` — a clean `pip install -e .` (or `-e ".[dev]"`) picks them up. (These were missing from `pyproject.toml` for a while despite being imported by `auth` — only present in this sandbox's `.venv` because they'd been pip-installed ad hoc — fixed once this actually broke a fresh install.)

`bcrypt` is pinned `<4.1` in `pyproject.toml` — `passlib` 1.7.4 (unmaintained since 2020) calls `bcrypt.__about__` and relies on old truncation behavior that `bcrypt>=4.1` removed; without the pin, every `hash_password()`/`verify_password()` call (so every test using the `tenant_a`/`tenant_b`/`make_tenant` fixtures) fails with `ValueError: password cannot be longer than 72 bytes`. If this pin is ever removed, expect the whole suite to break at fixture setup, not at whatever test happens to run first.

**Do not `pip install httpx2`, despite what a `StarletteDeprecationWarning` may suggest.** Recent `starlette` (the one this environment resolves to `fastapi`'s pin) nags `starlette.testclient` users to install a package called `httpx2` instead of `httpx`. Checked directly against PyPI: `httpx2` is a *different, unrelated* package that falsely claims to be a "continuation" of `httpx` under Pydantic's stewardship — no such maintainer transfer occurred; the real `httpx` is maintained by Encode. This reads as a typosquat riding on `starlette`'s real (optional, `[full]`-extra) dependency on it. The actual fix for the `RuntimeError: starlette.testclient module requires the httpx2 package` error is installing the genuine `httpx` (already declared correctly in `pyproject.toml`'s `dev` extra) via `pip install -e ".[dev]"` — `starlette` only *warns* about deprecation when real `httpx` is present, it doesn't error.

## Architecture

FastAPI + SQLAlchemy 2.0 (ORM, not Core) + Alembic + PostgreSQL (via `psycopg` v3), Pydantic v2 for schemas/settings. Multi-tenant SaaS: almost every domain entity belongs to an `Organization`.

### Module structure

Code lives under `app/modules/<name>/`, each module following the same file split:

- `models.py` — SQLAlchemy `Base` subclasses (see `app/core/database.py` for `Base`)
- `repository.py` — DB queries only, subclasses `BaseRepository[Model]` (`app/common/repository.py`), constructed as `Repository(db: Session)`
- `service.py` — business logic; owns transaction boundaries (`self.db.commit()` / `rollback()`), converts models to response schemas
- `schemas.py` — Pydantic request/response models
- `router.py` — FastAPI `APIRouter`; each router defines its own `get_<name>_service(db = Depends(get_db_session)) -> XService` provider
- `exceptions.py` — module-specific exceptions subclassing the shared ones in `app/common/exceptions.py`

Existing modules: `auth`, `organization`, `product`, `product_version`, `role`, `user`, `rbac`, `source`, `source_version`, `source_location`, `requirement`, `requirement_version`, `rule`, `rule_version`, `regulatory_basis_release`, `product_market_state`, `assessment_run`, `requirement_result`, `finding`, `state_snapshot`, `market_readiness`, `internal_role_assignment`.

`app/common/enums.py:UnknownBehavior` (`FAIL_CLOSED`/`REQUEST_INPUT`/`HUMAN_REVIEW`) is the one enum shared across modules rather than duplicated per-module — both `requirement_version` and `rule_version` import it. This is a deliberate exception to the usual "every module gets its own status/vocabulary enum even where values overlap" rule (see `ProductVersionStatus` vs. `SourceVersionStatus` vs. `RequirementVersionStatus` vs. `RuleVersionStatus`, four separate near-identical six-state enums, never shared) — `UnknownBehavior` is a genuinely cross-cutting policy concept C5 and C6 both describe in near-identical language, not a per-entity lifecycle. Don't reflexively move other overlapping enums into `app/common/` on this precedent without the same kind of textual justification.

`audit` owns the transactional outbox (`app/modules/audit/models.py:OutboxEvent`) — no `router.py`/`schemas.py`, since there's no public API for outbox rows in this milestone. Domain modules depend on it one-directionally (`organization`/`user`/`product_version` import `OutboxRepository`; `audit` imports nothing domain-specific back).

New modules should copy this same five/six-file shape and get wired into `app/main.py` (`create_app()`: import the router, `app.include_router(...)`) and into `app/models.py` (imported there so Alembic's `target_metadata` picks it up — see `migrations/env.py`, which imports `app.models`).

**`product_version` is the first nested-resource module** — its router (`app/modules/product_version/router.py`) is mounted at `/products/{product_id}/versions` instead of a flat top-level prefix. Its service resolves `product_id` through `ProductRepository.get_by_id(organization_id, product_id)` and 404s before doing anything version-related, so a `product_id` belonging to another org can't be used to list/create/read versions — the same "resolve the parent through the tenant boundary first" shape as the `role_id` fix in `rbac/service.py`. Its repository's `get_by_id` also takes `(organization_id, product_id, version_id)` — three args, not the `(organization_id, entity_id)` shape used by `Product`/`User`/`Role` — because a version fetched through the wrong `product_id` (even within the same org) should 404 too, not just across orgs. If you add another nested-resource module, follow this shape rather than the flat one.

### Regulatory content: `source` / `source_version` / `source_location`

Implements the RegNova spec's C4 (regulatory source model) + C9 (bitemporal versioning), modeling how a Malaysia cosmetics regulation, ASEAN directive annex, or RegNova interpretation is cited down to an exact section/article/page/table/paragraph coordinate.

- **Not organization-scoped, unlike every other module.** Per spec A2's scope table, canonical regulatory sources are "Supplied / validated by RegNova," not customer data — all orgs read the *same* `Source` rows. None of the three models carry `organization_id`; `SourceRepository`/`SourceVersionRepository`/`SourceLocationRepository` are correspondingly not org-scoped. Don't add `organization_id` here by reflex just because every other module has it.
- **`Source` is deliberately near-empty** (just `id`/timestamps) — descriptive fields (`title`, `issuing_authority`, `jurisdiction`, `tier`, `source_type`, `official_url`) live on `SourceVersion`, following C4.1's literal field placement rather than hoisting them onto `Source` for query convenience. This was a flagged, not obvious, choice — if querying "list all sources with their current title" without a join turns out to matter, revisit.
- **`SourceVersion.tier` is a plain `Integer` (1–4), not a string enum** like `status` — tier has real ordinal meaning the spec leans on (`tier <= 2` is a meaningful query), unlike `DRAFT`/`ACTIVE`/etc.
- **`SourceLocation` uses a compound coordinate** — `section`/`article`/`schedule`/`page`/`table_ref`/`paragraph` are independent nullable columns on one row (not a `location_type` enum + single value), since real citations are usually compound (e.g. "Section 5(2), Second Schedule, page 47"). At least one must be set — enforced by a Pydantic `model_validator` in `schemas.py`, not a DB constraint. Column is named `table_ref`, not `table` — the latter is a reserved SQL keyword.
- **`source_version` is nested under `source`** (`/sources/{source_id}/versions`, same shape as `product_version`: resolves `source_id` and 404s before touching versions, `get_by_id(source_id, version_id)` compound-scoped). **`source_location` is deliberately flat** (`/source-locations`, filterable by `?source_version_id=`), not nested a third level deep — `SourceLocationCreate` carries `source_version_id` as a body field instead of a path param, and the service validates it resolves to a real `SourceVersion` (404 if not) via `SourceVersionRepository.get_by_id_only(version_id)` — a second, unscoped lookup method distinct from the compound one `source_version`'s own nesting needs. This FK check is existence-only, not a tenant-boundary check like the `role_id`/`product_id` validations elsewhere in this codebase — there's no organization dimension on `SourceVersion` to cross.
- **Reads are open to any authenticated user** (`require_employee` — the first real use of that dependency in the codebase; every other module uses `require_manager`/`require_admin`) since Source is meant to be citable/visible to any customer user, gated more finely by `is_full_text_displayable` on the content itself, not by role.
- **Write endpoints (`POST`/`PUT` on all three) are gated behind `require_regulatory_content_writer`** (formerly a `require_admin` placeholder — resolved once the internal role model landed; see "Internal role model" below). It checks the caller holds an APPROVED `REGULATORY_KNOWLEDGE_LEAD` `InternalRoleAssignment`, not merely an ADMIN role in some organization — a customer-org admin can no longer create or edit `Source`/`SourceVersion`/`SourceLocation` rows at all, regardless of role.
- **No lifecycle audit trail**, mirroring `product_version`'s same gap: `SourceVersionService.update()` just overwrites `status`/`verified_at`/`recorded_at`/`activated_at`/`supersedes_id`/`superseded_by_id` in place via a generic `setattr` loop — no dedicated `verify()`/`activate()`/`supersede()` methods, no record of who transitioned what or when. When a new version supersedes an old one, the caller is responsible for setting **both** `old.superseded_by_id` and `new.supersedes_id` — nothing enforces they're kept in sync.
- `scripts/seed_regulatory_sources.py` — a one-off script (not wired into the app) that creates the first batch of `Source`/`SourceVersion` rows via the service layer directly (bypassing HTTP/RBAC entirely, since it's a data-curation operation, not a simulated customer request). All rows are `DRAFT` with a `notes` field stating they came from AI-assisted web research, not primary-source legal reading. Exercised against the SQLite test harness (`tests/test_seed_regulatory_sources.py`) but never run against a real Postgres database — none is available in this environment.

### Regulatory content: `requirement` / `requirement_version`

Implements C5 (requirement model). Same ownership model as `source` — no `organization_id`, reads via `require_employee`, writes via `require_regulatory_content_writer` (see the `source` section above and "Internal role model" below).

- **`Requirement` vs. `RequirementVersion` split**: unlike C4.1 (which named its field table "Required Source Version fields," making the split fairly explicit), C5 doesn't say which of its eight field groups live on `Requirement` vs. `RequirementVersion`. The decision made here: `Requirement` stays a thin identity anchor (`id` + `human_reference`, mirroring `Source`'s shape) and **all eight C5 field groups — including Scope — live on `RequirementVersion`**. The tell is C5's own definition: *"A Requirement Version is the effective, source-backed expression of that obligation **for a defined context**"* — "for a defined context" reads as Scope being part of what a version pins down, not a fixed property of the stable concept. Flagged as a judgment call, not a certainty, when this was proposed.
- **`dimension` + `context`**: the spec's "product/ingredient/claim/document/test context" bullet isn't five separate typed columns — the actual shape of "context" varies completely by which of B3's eight dimensions a requirement targets. Modeled as a real `dimension` column (matching B3's eight dimensions exactly: `CLASSIFICATION_ELIGIBILITY`/`INGREDIENTS`/`CLAIMS`/`LABEL`/`DOCUMENTS`/`TESTING`/`REPRESENTATION`/`REGISTRATION_READINESS`) plus a `context` JSON column (schema-versioned via `context_schema_name`/`context_schema_version`), leaning on C3's explicit allowance for schema-versioned JSON payloads alongside relational ownership. Same schema-versioned-JSON treatment for `applicability_predicate` (a "constrained predicate," read as the same kind of constrained-declarative-expression C6 describes for Rule's Condition component, not free code).
- **`unknown_behavior`** reuses C6's own three-value vocabulary verbatim (`FAIL_CLOSED`/`REQUEST_INPUT`/`HUMAN_REVIEW`, defined once as `app.common.enums.UnknownBehavior` and imported here — not redefined locally) — C5's "explicit unknown behavior" and C6's "Unknown policy" read as the same concept at two layers of the system.
- **`subject_kind`** (nullable, `DOCUMENT`/`CONSISTENCY_CHECK`, null = `DOCUMENT`) — added when Documents was built, only meaningful for `dimension == "DOCUMENTS"`. Lets `AssessmentRunService` split a dimension's active rules into two independently-evaluated subject pools (per-document checklist items vs. caller-supplied `consistency_checks[]`) without inferring routing from an `obligation_type` string prefix — same precedent as `StepRun.unknown_reason`: routing correctness shouldn't depend on a rule author remembering a naming convention. See "Assessment engine" below.
- **`default_severity`** reuses B4's Finding severity vocabulary verbatim (`CRITICAL`/`MAJOR`/`MODERATE`/`MINOR`/`INFORMATIONAL`) — B4 explicitly frames Finding severity as inherited from the requirement.
- **`authority_interpretation_label`** reuses FR-11's exact four-value vocabulary (`AUTHORITY_REQUIREMENT`/`RECOGNISED_STANDARD`/`REGNOVA_INTERPRETATION`/`SECONDARY_RESEARCH`), which maps 1:1 onto `Source`'s four tiers — **independently settable, not derived from linked `SourceLocation`/`SourceVersion` tiers.** That non-derivation was an explicit decision, not an oversight — flag it if it turns out the two should actually stay in sync.
- **`verification_level` is a plain open `String`, not an enum** — deliberately not reusing A6's Trust States (`AI_ASSESSED`/etc.), since "verification level" for evidence policy isn't independently defined anywhere in the spec. Treat this the same way as `obligation_type`: needs real definition from RegNova's Regulatory Knowledge Lead before it's worth constraining to a closed vocabulary.
- **Temporal fields use the exact same names as `SourceVersion`** — `effective_from`/`effective_to`, `recorded_at`/`retired_at`, `supersedes_id`/`superseded_by_id`. C5's own Temporal group lists "valid-from/to" as a field distinct from "effective-from/to," which doesn't match C9's bitemporal table (only one system-time pair, expressed as `recorded_at`/`retired_at` point-in-time timestamps, not a named range). Resolved as: "valid-from/to" is C5's phrasing for that same `recorded_at`/`retired_at` axis, not a third temporal concept — so `RequirementVersion` reuses those two field names directly rather than introducing `valid_from`/`valid_to` as new terminology. "Included basis releases" is deferred exactly like `SourceVersion`'s "release membership" — not built, will be a join table once Regulatory Basis Release exists.
- **Provenance's "one or more source-location links"** is a plain many-to-many association table (`requirement_version_source_locations` — `RequirementVersionSourceLocation` in `requirement_version/models.py`), not a dedicated five-file linking module — it carries no independent lifecycle, just `requirement_version_id` + `source_location_id`. Exposed on `RequirementVersionCreate`/`Update` as `source_location_ids: list[UUID]`; the service validates every id resolves to a real `SourceLocation` (404 if not) via `SourceLocationRepository.get_by_id()` (looped per id — fine at this scale, revisit if it ever needs to be bulk). `update()` treats `source_location_ids` as PATCH-replace-the-whole-set semantics when explicitly provided (checked via `payload.model_fields_set`, not just truthiness, so an explicit empty list correctly clears all links rather than being indistinguishable from "not provided").
- **Applicability outcomes (C5.1: Applies/Does Not Apply/Unknown/Conflict) are NOT stored on `RequirementVersion` at all.** `status` describes the content's own review maturity; an applicability outcome describes the *result of evaluating* a specific `RequirementVersion` against a specific product/context at assessment time — C10 confirms this belongs to a future "Requirement Result" entity produced by an Assessment Run, not built in this milestone. C5.1's retention requirement (*"that decision must retain its predicate inputs and source/rule lineage"*) is a hard constraint on whatever builds that entity: it needs `outcome` (the four-value enum), a JSON snapshot of the actual `predicate_inputs` evaluated, and **relational** (not JSON-buried) links to the `RequirementVersion`, `RuleVersion`(s) (once C6 exists), and `SourceLocation`(s) involved — per C3's rule that lineage must stay a queryable relational key. The B5.2 business rule ("only Does Not Apply excludes from the readiness denominator") is enforced wherever that future entity's aggregation logic lives, not here.
- Same lifecycle-audit-trail gap as `source_version`/`product_version`: `update()` just overwrites fields via `setattr`, no dedicated `verify()`/`activate()`/`supersede()` methods.

### Regulatory content: `rule` / `rule_version`

Implements C6 (rule model) — executable logic that evaluates a `RequirementVersion` against product facts. Same ownership model as `source`/`requirement` — no `organization_id`, `require_employee` reads, `require_regulatory_content_writer` writes.

- **`Rule` vs. `RuleVersion` split**: C6's own prose only ever says *"A Rule Version is..."* and never separately defines "Rule" the way C5 did for Requirement ("A Requirement is a stable... A Requirement Version is..."). The split is real anyway — confirmed by **C2's entity catalog** (`Requirement, Requirement Version, Rule, Rule Version, Applicability Predicate, Regulatory Basis Release` — `Rule` and `Rule Version` listed as separate nouns) and **Appendix 1's glossary**, which defines `Rule` on its own (*"Constrained machine-executable logic that evaluates facts against a requirement or derives a controlled result"*). `Rule` stays a thin identity anchor (`id` + `human_reference`), same shape as `Source`/`Requirement` — this specific field split isn't independently confirmed by C6's own text, just consistent with precedent.
- **`condition` is a recursive JSON condition tree**, not free code: leaf nodes (`{"op": "equals"|"not_equals"|"in"|"not_in"|"gt"|"gte"|"lt"|"lte"|"exists"|"not_exists", "field": ..., "value": ..., "normalize": "<fn name>"}`) and combinator nodes (`{"op": "all"|"any", "conditions": [...]}`), directly mapping onto C6's own Condition row (*"equality, membership, numeric/date comparison, any/all, existence and approved normalization functions"*) and corroborated by line 949 (*"Rule authoring uses a constrained declarative schema/DSL; arbitrary code or model-generated code execution is prohibited"*). **No registry of approved normalization functions exists anywhere in the spec** — `normalize` references a function name from an allow-list that doesn't exist yet.
- **Not modeled as a normalized entity, despite C2 listing "Applicability Predicate" as its own noun** in the same bounded context as `Requirement`/`Rule` (separate from both). There's no dedicated spec section (no `C6.x`) defining what that entity would contain, so both `RequirementVersion.applicability_predicate` and `RuleVersion.condition` stay inline schema-versioned JSON rather than FKs to a shared entity. **Flagged as unresolved, not decided** — if a normalized entity turns out to be the real intent, both fields need revisiting together.
- **`requirement_version_id` is a nullable single FK, not many-to-many.** C6's Provenance row (*"Requirement Version and Source Location(s) the rule operationalizes"*) marks "Source Location**(s)**" plural but not "Requirement Version" — read as one rule version operationalizing at most one requirement version. Nullable because C6's Output row includes `CALCULATION_COMPONENT` as a possible output type, which reads like some rules may be shared computational utilities not tied to a specific requirement. `RequirementVersionRepository` gained a new `get_by_id_only(version_id)` (unscoped, mirrors `SourceVersionRepository`'s own method) since `rule_version` only ever has the bare id, not the parent `requirement_id` needed by the compound `get_by_id`.
- **`inputs`/`inputs_schema_name`/`inputs_schema_version`**: the field's existence and content are directly grounded in C6's own Inputs row (*"Typed fields from a published Product Version, verified extraction, market/pathway or prior rule output"*). The schema-versioning wrapper around it is **not** spec-stated — it's a judgment call, applied by analogy to `RequirementVersion.applicability_required_inputs` (itself already an analogy-based choice, not something C5 specified either). Flagged as a compounding analogy, not a double-confirmed pattern.
- **`test_fixtures` is inert JSON data only** (`{input_facts, expected_output}` pairs, schema-versioned) — corroborated by C6's Governance row ("test fixtures") and line 2287 ("deterministic test fixtures"). **No execution engine built** to actually run fixtures against `condition` — that's real, separate scope.
- **`Safety` (C6: "No arbitrary code, network calls, model calls or side effects inside rule evaluation") is not a field** — it's an engineering constraint on whatever future evaluation engine executes `condition` against product facts, which isn't built in this milestone. `RuleVersion` only stores the logic definition, never runs it.
- **Rule and Requirement version independently — they don't have to change together.** C9.1 describes a Regulatory Basis Release as *"immutable, content-addressed and contains exact IDs/hashes of included Source, Requirement and Rule Versions"* — a snapshot of whatever combination of currently-approved versions exists when a release is cut, not a claim the three lineages move in lockstep. A `RequirementVersion` can change with no corresponding new `RuleVersion` yet; detecting that drift is C11's job ("Change events and impact propagation," unread, not this milestone) — `RuleVersion.requirement_version_id` just records what a specific rule version was built against, it doesn't detect staleness.
- `rule_version_source_locations` is a separate association table from `requirement_version_source_locations` (same shape, different FK column name) — not a shared/polymorphic link table. Consistent with keeping per-model association tables rather than introducing a new kind of schema flexibility not asked for.
- Same lifecycle-audit-trail gap as every other version-bearing module here.

### Regulatory content: `regulatory_basis_release`

Implements C9.1 (release invariants) — the immutable manifest of approved `SourceVersion`/`RequirementVersion`/`RuleVersion` combinations pinned by assessments. Same ownership model as `source`/`requirement`/`rule` — no `organization_id`, `require_employee` reads, `require_regulatory_content_writer` writes.

- **Fields built against C9.1's precise "Release invariants" text, not line 1049's looser scene-setting paragraph.** Line 1049 says a release's manifest *"also records model/prompt/parser versions and document/evidence versions used"* — but cross-checked against C10's own lineage table (*"document versions, source/rule/requirement versions, engine build, configuration hash, model/prompt/parser versions, timestamps"*), that's almost verbatim a **State Snapshot's** lineage, not Release's. C9.1 itself only says *"exact IDs/hashes of included Source, Requirement and Rule Versions plus configuration."* Built against C9.1: no `model_version`/`prompt_version`/`document_version` fields on this model — those belong to a future State Snapshot (C10, not this milestone).
- **`jurisdiction`/`market` fields are inferred, not C9.1-stated** — added because the formula right above C9 (*"Product Version × Market × Regulatory Basis Release × Assessment Run = Regulatory State Snapshot"*) treats Release as inherently market-scoped; without it, "the current release" has no scope to be current *for*.
- **3-state lifecycle** (`RegulatoryBasisReleaseStatus`: `ACTIVE`/`SUPERSEDED`/`ARCHIVED`), not the six-state `DRAFT`/`IN_REVIEW`/`VERIFIED`/`ACTIVE`/`SUPERSEDED`/`ARCHIVED` used by `SourceVersion`/`RequirementVersion`/`RuleVersion`. C9.1 calls Release immutable outright (no editable draft phase implied), and line 945's lifecycle enumeration names all three Version types but excludes Release — the reviewing already happened at the component-version level before inclusion. Interpretation, not certainty.
- **`content_hash`** is the "content-addressed" mechanism — SHA-256 over the sorted set of included version UUIDs (all three types) plus `configuration`, computed once at creation (`_compute_content_hash` in `service.py`), `UNIQUE`-constrained so two releases can never have byte-identical regulatory content. **Not** literal `id = hash(content)` — `id` stays a normal `UUIDMixin` UUID like every other model, avoiding a one-off PK convention that would complicate every FK pointing at a release.
- **"IDs/hashes of included versions" (C9.1) is satisfied at the Release level only, not per included version.** `SourceVersion` has `file_checksum`/`canonical_text_checksum` to snapshot; `RequirementVersion`/`RuleVersion` have no checksum field at all (C5/C6 never called for one). Rather than retrofitting checksums onto two already-shipped models, the three join tables (`regulatory_basis_release_source_versions`/`..._requirement_versions`/`..._rule_versions`) store IDs only — `content_hash` on the release itself is the actual integrity mechanism. **Flagged as a real gap, not silently resolved** — if per-version hash snapshotting turns out to be the real intent, this needs revisiting alongside adding checksum fields to the other two models.
- **Inclusion eligibility is checked at creation, not left to the caller**: every referenced version must have `status == 'ACTIVE'` **and** `verified_at is not None`. The `status` check alone is grounded in line 1162 (*"Only Verified + Active Rule Versions in the pinned Regulatory Basis Release may drive deterministic production outcomes"*) — both conditions, not either. The `verified_at` check is deliberately defensive on top of that: nothing in this codebase currently enforces that a version can only reach `ACTIVE` by passing through `VERIFIED` first (every version's `update()` is a generic `setattr` loop — see the repeated lifecycle-audit-trail gap noted throughout this file), so a version could reach `status == ACTIVE` with `verified_at` still `NULL`. `test_create_release_with_active_but_unverified_version_is_rejected` exercises exactly this gap, distinct from the more obvious still-`DRAFT` rejection case.
- **`RegulatoryBasisReleaseUpdate` is deliberately narrow** — only `status`, `notes`, `reviewer_user_id`, `verified_at`, `retired_at`, `superseded_by_id`, `effective_to`. This is an intentional exception to the Create/Update pattern used everywhere else in this codebase (Update usually mirrors Create plus workflow fields) — `jurisdiction`/`market`/`configuration`/the three `*_version_ids`/`supersedes_id`/`effective_from` are excluded because they define the release's immutable content identity, and C9.1's "immutable" framing for Release is stronger than "immutable once published" for the Version-bearing models (which at least have an editable `DRAFT` phase first).
- **Active-release conflict + atomic supersession, enforced in `create()`** (the one piece of this session's regulatory-content work with real business-rule enforcement, not just a flagged gap): creating a new `ACTIVE` release when one already exists for the same `(jurisdiction, market)` is rejected (`RegulatoryBasisReleaseAlreadyActive`, 409) **unless** `supersedes_id` explicitly points at that exact existing active release — in which case the old release is flipped to `SUPERSEDED` (with `superseded_by_id` set and `retired_at` stamped) in the *same* `create()` transaction/commit as the new release's insert, so the database is never observably in a state with two simultaneously-active releases for one jurisdiction, nor in a state with zero. `IntegrityError` on `content_hash`'s unique constraint is caught and re-raised as `RegulatoryBasisReleaseDuplicateContent` (409), matching the `try`/`except IntegrityError` pattern already used in `organization`/`role` services.
- **`activated_at`'s real C9 meaning — "Inclusion in a production Regulatory Basis Release" — is not yet wired up.** Right now `activated_at` on `SourceVersion`/`RequirementVersion`/`RuleVersion` is just another field in each one's own generic `update()`. The *correct* trigger, now that Release exists, is Release's own `create()` setting `activated_at` on every version it includes — **not retrofitted in this pass**, flagged when Release was first proposed and still true: touching this would mean changing three already-shipped modules' `update()` behavior, out of scope for adding Release itself.

### `product_market_state` (FR-03)

Implements FR-03 (Product × Market state) — the persistent binding of a customer's Product to a market, holding pointers to the product version currently being evaluated there and the Regulatory Basis Release pinned for that market. Unlike every other module in the "Regulatory content" set above, this is **customer data, not regulatory content** — organization-scoped like `Product`/`User`/`Role`, reusing `Product`'s own RBAC pattern (`require_manager` reads, `require_admin` writes) with no placeholder caveat, since there's no RegNova-staff-actor-model gap to flag here.

- **Not a versioned entity, despite sitting right next to Source/Requirement/Rule/Release in this codebase.** Those four are all "stable identity + immutable versioned children, chained by `supersedes_id`/`superseded_by_id`." `ProductMarketState` is deliberately **a single mutable row per `(organization_id, product_id, market)`** — FR-03's own language ("holds a pointer to **current** product version and regulatory-basis release") describes a pointer that moves, not a lineage that chains. No `status` transition history, no supersession — `update()` just overwrites fields via `setattr`, same shape as every other version-bearing module's known lifecycle-audit gap, except here there's no lifecycle to audit in the first place, just a two-state `status` (`ACTIVE`/`ARCHIVED`) distinct from the `gate` field.
- **Tenant-scoped**, confirmed via C1.1's State Snapshot identity field group, which explicitly lists `organisation_id` alongside product/market/release — this is the one place in the "Regulatory content" family that crosses back into customer-owned territory, since it's the customer's own product being evaluated, not the regulatory content itself.
- **`market` is a plain string**, not `market_id` — matches the precedent already set on `RequirementVersion`/`RegulatoryBasisRelease`; the spec's own `_id`-suffixed field names elsewhere (`category_id`, `pathway_id`) aren't literally FK-shaped either.
- **`gate` reuses B5.3's G0–G5 readiness vocabulary verbatim** (`G0` Assessment Incomplete … `G5` Authority Confirmed), defaulting to `G0` on creation — distinct from `status`, which just tracks whether this binding itself is live or archived.
- **`create()` is get-or-create, idempotent on `(organization_id, product_id, market)`** — the one service method in this codebase with genuine get-or-create semantics rather than insert-or-409. A second `create()` call for the same product+market returns the existing row **unchanged**, even if the request's `product_version_id` differs from what's already pinned — it does not silently repoint the existing row to a new version. Repointing is an explicit `update()`, not an implicit side effect of `create()`.
- **DB-level partial unique index, not just the service-layer idempotent check**: `uq_pms_active_per_product_market` enforces at most one `ACTIVE` row per `(organization_id, product_id, market)` at the database level (`postgresql_where`/`sqlite_where` both set to `status = 'ACTIVE'` — **both dialect kwargs are required**; empirically verified that omitting `sqlite_where` silently produces a full, non-partial unique index on SQLite, which would then wrongly reject legitimate `ARCHIVED` duplicates). `create()` still does its idempotent pre-check first as the common-case fast path, but a genuine race (two concurrent requests for the same first-ever state) is caught via `IntegrityError` on the insert, rolled back, and resolved by re-querying for the now-existing active row — same idempotent return value either way, just reached via a different path. `tests/test_product_market_state.py::test_partial_unique_index_rejects_duplicate_active_rows` and `::test_create_handles_race_by_returning_existing_active_state` exercise the index and the race path directly.
- **`RegulatoryBasisRelease`'s own active-release-per-jurisdiction check has this exact same unenforced-race gap and does not yet have the DB-level partial-index treatment** — its `create()` only has the service-layer pre-check (see the "Regulatory content: `regulatory_basis_release`" section above). Flagged as a known follow-up, not fixed in this pass, per explicit instruction when this module was built — if it's ever fixed, `RegulatoryBasisReleaseStatus.ACTIVE`-scoped partial index on `(jurisdiction, market)` is the natural analogue of `uq_pms_active_per_product_market`.
- **Regulatory Basis Release resolution at creation**: `create()` looks up the currently-`ACTIVE` release for the given `market` via `RegulatoryBasisReleaseRepository.get_active_for_jurisdiction(jurisdiction, market)`, passing `payload.market` for **both** positional args — `ProductMarketState` only has one market/jurisdiction field (FR-03), unlike `RegulatoryBasisRelease` itself, which has both. If no active release exists yet for that market, `regulatory_basis_release_id` is simply left `null` rather than rejecting creation — FR-03's own framing (creating this row "just establishes 'this product is being evaluated for this market'... producing an empty shell") treats an as-yet-unpinned release as a valid starting state, not an error.
- **Product version eligibility**: `product_version_id` must resolve to a real, currently-`is_active` `ProductVersion` for that product (404 if it doesn't resolve at all, 409 `ProductMarketStateIneligibleProductVersion` if it resolves but has been withdrawn) — no auto-resolution of "the current product version" happens here; the caller must name a specific version.
- **What's deliberately NOT here, reserved for the future Assessment Run layer (C10)**: no dimension states, no findings, no readiness computation, no Assessment Run linkage. `ProductMarketState` is the stable anchor an Assessment Run will attach to (via `product_id`/`market`), not a place that stores assessment results itself — same boundary C5.1 already drew for `RequirementVersion` (applicability outcomes belong to a future "Requirement Result," not the requirement content itself).

### Assessment engine: `app/engine`, `assessment_run`, `requirement_result`, `finding`

Implements C10's "Rule evaluation" lineage hop only - now covers three dimensions (Claims, then Label as the second vertical slice, then Documents as the third - all reusing the same engine/models unchanged in shape). Deliberately **not** built in this pass: the AI/LLM layer (D2-D6 - Claims Analyst/Label Analyst, confidence scoring, human approval matrix - a separate, much larger build), State Snapshot (C10's top-level aggregate across all dimensions + approvals), and `ProductMarketState.gate` recomputation (needs all eight dimensions, not just the three built so far).

- **`app/engine/condition_evaluator.py` is a pure, side-effect-free function library with no DB model of its own** - filed as a new top-level package parallel to `modules`/`common`/`core` rather than under `app/modules/`, since D2 explicitly frames "Deterministic rules" as one of five distinct architecture layers, not a domain module. `evaluate_condition(condition, facts)` walks a `RuleVersion.condition` tree and returns a three-valued (`MATCH`/`NO_MATCH`/`UNKNOWN`) `EvaluationResult` carrying a `trace` (satisfies C10's "deterministic trace" lineage-metadata requirement) and `missing_fields`.
  - **Three-valued (Kleene) logic for `all`/`any` combinators** - not spec-stated explicitly (C6 only lists the operator vocabulary), flagged as an inferred but standard semantic when this was proposed: a definite `NO_MATCH` always wins an `all` regardless of sibling `UNKNOWN`s; a definite `MATCH` always wins an `any`.
  - **`exists`/`not_exists` never produce `UNKNOWN`** - absence is the very thing being tested, not a gap in the ability to test, unlike every other operator (which needs the value present to compare against).
  - **The normalize function registry (`lowercase`/`strip`/`collapse_whitespace`) is a deliberately tiny placeholder**, not the real registry C6 gestures at ("approved normalization functions") - already flagged elsewhere in this file that no such registry exists anywhere in the spec; this is just enough for synthetic Claims fixtures. An unrecognized `normalize` name raises `UnknownNormalizeFunction`, caught per-`StepRun` (see below), not silently ignored.
  - **Facts are always one flat, scalar-valued subject - the engine never traverses arrays itself.** For Claims, `AssessmentRunService` iterates the claim set and evaluates each applicable rule once per claim; the condition DSL never grew an array/each construct. This was the core answer to "what does input facts look like for Claims" and was confirmed explicitly before implementation.
  - **A field's resolved value may be a plain scalar (Claims, untouched) or a `{"value": ..., "confidence": ...}` wrapper (Label's OCR-extracted fields, and any future extraction-backed dimension)** - `_is_confidence_wrapped` requires both keys present; a dict with only `"value"` is treated as a non-wrapped value, not confidence-gated, matching plain-dict-comparison semantics rather than silently defaulting confidence to something. When wrapped and below threshold, the leaf resolves `UNKNOWN` with `reason="low_confidence"` in `EvaluationResult.unknown_reason` and the trace entry - the same outcome as a missing field, but distinguishable so a reviewer (and `AssessmentRunService`, see below) can tell "customer needs to supply this" from "RA needs to eyeball this OCR read." `exists`/`not_exists` ignore confidence entirely - they test presence/the extraction attempt happening at all, not whether the value found is trustworthy enough to compare.
  - **`DEFAULT_MIN_CONFIDENCE = 0.5`, hardcoded in `app/engine/condition_evaluator.py`** - not a placeholder guess. D5.1's own hard-cap table gives this exact number ("Low-confidence OCR on mandatory label field | ≤0.49 | RA visual check"), and Appendix 4 explicitly lists confidence-threshold ratification as a RegNova-owned decision that "this pack supplies defaults" for. A leaf can override with its own `min_confidence`; when it doesn't, any confidence-wrapped field still gets gated against this default - a rule author can't accidentally skip the check by forgetting to set one. **Known limitation, flagged not built**: this value is hardcoded rather than sourced from `RegulatoryBasisRelease.configuration`, which is where B5.2's own precedent says versioned regulatory thresholds should live - the engine is currently a pure function with no release context threaded into it, so wiring that through is real plumbing this pass didn't do.
  - **Combinators merge `reason` the same worst-first way they merge `outcome`**: if any contributing `UNKNOWN` child has `reason="low_confidence"`, the merged reason is `low_confidence` (forcing human review at the root) even if siblings were merely missing.

- **`assessment_run`** (`AssessmentRun`/`StepRun`/`DimensionAssessment`) - org-scoped like `ProductMarketState`; `require_manager` reads, `require_admin` triggers a run (same RBAC pattern as `product_market_state`, no placeholder needed - this is genuine customer data, not the RegNova-staff-actor-model gap).
  - **`AssessmentRun.product_version_id`/`regulatory_basis_release_id` are snapshotted at creation from `ProductMarketState`, not live FKs to it** - `ProductMarketState`'s own pointers are mutable (a single row per product+market) and can move after a run starts; AC-FR-05-01 requires the run to stay reproducible from exactly what it pinned.
  - **Execution status (`QUEUED`/`RUNNING`/`COMPLETED`/`FAILED`/`CANCELLED`) is a new, minimal vocabulary - deliberately NOT FR-05's own "Preflight Failed → Queued → Assessing → AI Assessed → RA Review → ..." list**, which describes the *resulting* dimension/gate state, not the run's own execution lifecycle.
  - **Runs entirely synchronously within the request - no job queue exists.** Confirmed acceptable for this first vertical slice rather than stubbing an async shape now. **Revisit trigger, logged here per that confirmation: once a second dimension is implemented (multiplying a single run's rule count) or a real product's claim set grows past a handful of items, synchronous per-request execution will start timing out HTTP requests - move to the outbox/worker pattern already used by `audit` at that point, not before.**
  - **`StepRun` is the universal execution ledger - written for every rule evaluated, regardless of `output_type`.** `RequirementResult`/`Finding` are semantic artifacts derived from only a subset of `StepRun`s (`APPLICABILITY`/`REQUIREMENT_RESULT` → `RequirementResult`; `FINDING_PROPOSAL` → `Finding`), not written for all six `RuleOutputType` values. This distinction mattered concretely: a `FINDING_PROPOSAL` rule under `REQUEST_INPUT` creates neither a `RequirementResult` nor a `Finding` (see the mapping table below) - `DimensionAssessment`'s state derivation has to scan `StepRun.outcome` directly to still catch that signal, not just `RequirementResult`, or a missing-input case silently reads as `COMPLIANT`. This was caught by `tests/test_assessment_run_claims.py::test_request_input_missing_creates_no_finding_and_pending_input` failing before the fix, not anticipated in the design.
  - **`EVIDENCE_REQUEST`/`WORKFLOW_GATE`/`CALCULATION_COMPONENT` are stubbed** - `StepRun` still executes and records the raw engine result, but nothing consumes it further. No Evidence/Document model exists yet (C8 unbuilt) and no workflow engine exists.
  - **UnknownBehavior → outcome mapping** (the first real consumer of that field - previously stored on `RuleVersion` but never read):

    | unknown_behavior | `APPLICABILITY` rule | `REQUIREMENT_RESULT` rule | `FINDING_PROPOSAL` rule |
    |---|---|---|---|
    | `FAIL_CLOSED` | outcome=`APPLIES` (stays in scope - excluding it would be the "default pass" C6 forbids) | outcome=`NOT_SATISFIED` | Finding proposed anyway; `rationale` records it was forced |
    | `REQUEST_INPUT` | outcome=`UNKNOWN` | outcome=`UNKNOWN` | no Finding - `EVIDENCE_REQUEST` is the spec's real vehicle for "need more data," not a substituted Finding |
    | `HUMAN_REVIEW` | outcome=`UNKNOWN` | outcome=`UNKNOWN` | Finding proposed; `rationale` records it needs review |

    This exact mapping isn't spelled out in C6 (only "never default pass") - it's an inference, confirmed with the user before implementation. `RequirementResult.outcome == "UNKNOWN"` can only ever result from `REQUEST_INPUT` or `HUMAN_REVIEW` (never `FAIL_CLOSED`, which always resolves to a definite value) - downstream code distinguishes the two by joining back to `rule_version.unknown_behavior`, not a redundantly stored reason.
  - **`DimensionAssessment.state` derivation precedence (worst-first, mirroring B5.3's own gate philosophy)**: any proposed `Finding` or `NOT_SATISFIED` result → `NON_COMPLIANT`; else any engine error, `HUMAN_REVIEW`-sourced unknown, or `low_confidence`-sourced unknown → `HUMAN_REVIEW_REQUIRED`; else any `REQUEST_INPUT`-sourced unknown → `PENDING_INPUT`; else every result `DOES_NOT_APPLY` → `NOT_APPLICABLE`; else `COMPLIANT`. Only six of B3's twelve dimension states are reachable at all by a rule-only engine - `RegNova Verified`/`Customer Action Required`/`Authority Confirmed` need review/workflow layers this slice doesn't build. Not spec-stated explicitly; confirmed with the user before implementation.
  - **`_run_subject_list_dimension` accepts a flat, non-list fact set for any dimension other than `LABEL`, not just the `"claims": [...]` list shape.** Originally, the non-`LABEL` branch unconditionally read `dimension_facts.get("claims", [])` - any dimension using this method (i.e. every dimension except `LABEL`/`DOCUMENTS`) that submitted facts under any other shape silently resolved zero subjects, zero `StepRun`s, and read `UNKNOWN` - indistinguishable from a dimension with no rule content at all. Caught auditing known limitations against an upcoming multi-category test corpus (nutraceutical dosage limits, medical-device risk classification - neither naturally list-shaped) before any corpus content was written, not by a failing test. Resolved: if `"claims"` is present, behavior is unchanged (a dimension that genuinely wants list iteration - e.g. one dosage check per ingredient - can still use it); otherwise, if `dimension_facts` is non-empty, the whole payload minus `"product"` becomes ONE implicit subject with `subject_key=None`; otherwise zero subjects, same as before. `_run_subject_list_dimension` now returns the resolved subject count so `_run_dimension` can tell "zero subjects because nothing was submitted/matched" apart from "zero subjects because this dimension has no rules at all."
  - **New `DimensionAssessmentState.NO_SUBJECTS_RESOLVED`, distinct from both `UNKNOWN` and `PENDING_INPUT`.** When a dimension has active rule content but the flat-subject resolution above still produces zero subjects (nothing submitted, or an explicit empty `claims: []`), `_run_dimension` sets this state directly rather than calling `_derive_dimension_state` - with zero `StepRun`s either way, that method's own `if not steps: return UNKNOWN` can't distinguish "no rules exist" from "rules exist but nothing matched." Considered reusing `PENDING_INPUT` instead of a new state and rejected it: `PENDING_INPUT` is only ever derived from at least one existing `StepRun` (a rule WAS evaluated and a specific condition field was missing, per that rule's own `unknown_behavior`), so it's mechanically unreachable when zero `StepRun`s exist, and semantically it describes a different, later failure point (a precise per-field gap discovered during evaluation, vs. no subject existing to evaluate against at all). Only applies to the non-`DOCUMENTS` branch - `DOCUMENTS`' checklist is regulatory-basis-driven rather than caller-driven and has its own, structurally different version of this risk in its `consistency_checks[]` pool, deliberately not folded into this fix (see "Known limitations" below).
  - **`StepRun.unknown_reason`** (added when Label was built, via its own migration on the already-shipped `step_runs` table - not an edit to the Claims migration) mirrors `EvaluationResult.unknown_reason` (`"missing"`/`"low_confidence"`/`null`). A genuine new column was required, not just JSON already in `trace`: `DimensionAssessment`'s state derivation needs to know, per `StepRun`, whether that specific step's `UNKNOWN` was the confidence-forced case - looking up `rule_version.unknown_behavior` fresh from the DB (the pre-existing mechanism) can't tell that apart from the rule's own genuinely-declared policy. Caught while implementing Label, not anticipated in the Claims design - the original claim that "no StepRun changes needed" for confidence work was wrong and corrected once the full data flow was traced through.
  - **AC-FR-06-02 hard-pin: a `low_confidence`-reasoned `UNKNOWN` is always treated as `HUMAN_REVIEW`, regardless of what the triggering rule's own `unknown_behavior` declares.** Implemented via `AssessmentRunService._effective_unknown_behavior(result, rule_version)`, used everywhere `unknown_behavior` previously was, plus independent checks in `_maybe_propose_finding` (rationale wording) and `_derive_dimension_state` (dimension-state classification) - three call sites, not one, because a rule-level lookup alone can't see a specific step's confidence-forced override. All three were verified via weaken/confirm-fail/restore. This was a genuine fork, not an obvious extension of the Claims `UnknownBehavior` model - AC-FR-06-02's wording ("never silently passes... becomes Human Review Required") reads as a system invariant, not something a rule author's declared policy can weaken by choosing `FAIL_CLOSED`/`REQUEST_INPUT`, unlike a merely-missing field where the rule's own policy is respected. One concrete behavioral consequence worth remembering: for a `FINDING_PROPOSAL` rule, `REQUEST_INPUT` normally suppresses the Finding entirely for a missing field - it does **not** suppress it for a `low_confidence` field; a Finding is still proposed, with rationale explaining the override.
  - **Label's `label_fields[]` request-payload shape stays flat** (`{"field_key", "value", "confidence", "location"}` per item, matching what was proposed and confirmed) but the engine needs the confidence-gate to fire on one resolved field, so `AssessmentRunService._build_label_field_facts` nests `value`/`confidence` under a fixed internal `"extracted"` key before calling `evaluate_condition` - Label rule conditions reference `"field": "extracted"` to get confidence gating (e.g. `{"op": "equals", "field": "extracted", "value": "50 mL"}`). This wire-format nesting is an internal nuance discovered during implementation, not part of the documented request payload, which is why it wasn't spelled out in the original proposal. `field_key` (the checklist item, e.g. `"net_quantity"`) doubles as `subject_key` on `StepRun`/`Finding`, mirroring `claim_id` for Claims; `field_key` stays an open string, not a closed enum, same reasoning as `obligation_type`/`verification_level` - FR-06's checklist prose ("mandatory fields, manufacturer/importer statements, net quantity, warnings, language requirements, product identity, detected claims") isn't an exhaustive canonical list.
  - **A `label_fields[]` item with `value: null` (nothing extracted at all for that field) omits the `"extracted"` key entirely from the facts passed to the engine, rather than wrapping a null value.** Building the wrapper unconditionally would make the field structurally "exist" (as a null-valued wrapper) even when nothing was found, making `not_exists`/missing-field handling unreachable for exactly the case Label needs them most - a mandatory field that extraction found nothing for. Caught by a failing test during implementation, not anticipated in the design.
  - **"Detected claims" on Label (FR-06) is a self-contained check in this pass, not cross-referenced against Claims Review's (FR-07) own dimension results** - each dimension's `StepRun`s are independent within one `AssessmentRun`, and nothing in this model resolves cross-dimension dependencies. Confirmed explicitly as out of scope; genuine cross-dimension referencing (e.g. "does this on-label claim match an approved Claim Set entry") is C11/C13 territory, not something a second single-dimension slice should take on.
  - **`FindingRevision.observed_location`'s provisional shape (`{"page", "region"}`, left open pending C8's Document/page/region model) gets its first real use here** - `_maybe_propose_finding` threads `facts.get("location")` straight through from a Label field's `location` into the created revision.
  - **Documents (FR-08) is the third dimension, and the first whose checklist is regulatory-basis-driven rather than caller-driven.** For Claims/Label the caller enumerates the complete subject list; for Documents, `AssessmentRunService._run_documents_dimension` derives the checklist from the distinct `RequirementVersion`s referenced by the dimension's active rules (`obligation_type` doubles as `document_type`, same reuse pattern as `Finding.issue_type`) - confirmed explicitly against FR-08's "Checklist is generated from applicable Requirement Versions... users cannot remove a mandatory item" and AC-FR-08-01, rather than trusting the caller's submitted list to be complete. A required `document_type` the caller never submitted is still evaluated, as empty facts (`{"document_type": ...}` only) - the same missing-entirely detection Label's null-value fix established, just triggered by "caller never submitted this item" instead of "caller submitted a null field." Anything the caller submits with no matching checklist rule is simply not evaluated by this dimension (extras aren't part of the deterministic checklist either).
  - **A `documents[]` item's extracted fields (`manufacturer`, `expiry_date`, `issuer`, ...) arrive already `{"value", "confidence"}`-wrapped per field**, unlike Label's single flat `value`/`confidence` pair nested under one internal `"extracted"` key - a document has several independently-extracted fields at once, so each gets its own wrapper directly rather than one shared indirection key. `status` (`"uploaded"`/etc.) is passed through unwrapped - it reflects pipeline/presence state, not an extracted business value, and doubles as the "was anything genuinely submitted at all" presence marker for `not_exists` checks (distinct from "submitted but this specific field didn't extract," which a `not_exists` on that specific field detects instead). Same null-value-omission convention as Label: a field whose value is `None` is dropped from facts entirely (`AssessmentRunService._build_document_facts`), not built as a null-valued wrapper.
  - **`days_until_expiry` is computed server-side in `_build_document_facts`, not in the engine.** The engine must stay a pure function of `condition`+`facts` to keep `StepRun` replay deterministic (C10's "deterministic trace" requirement, and AC-FR-05-01's run reproducibility) - letting a condition leaf reference "today" or call `date.today()` internally would make the same stored `StepRun` evaluate differently on replay. Existing `gt`/`gte`/`lt`/`lte` operators are sufficient for the actual comparison (raw ISO-8601 date strings already sort correctly lexicographically = chronologically, so no date-parsing was added to the engine either) - what needed solving was *what* gets compared, not the comparison itself. `days_until_expiry` is derived from `expiry_date` and **`AssessmentRun.started_at`** (the run's own pinned timestamp, not wall-clock `now()`), so a stored run replays identically regardless of when it's replayed; it inherits `expiry_date`'s own confidence, since the day-count arithmetic itself adds no uncertainty beyond what the OCR read already carries. "Expiring Soon" needed no new outcome vocabulary value - it's expressed as ordinary `FINDING_PROPOSAL` rules at different `days_until_expiry` thresholds (e.g. 90/60/30/7, FR-08's own spec-stated defaults) with different severities per B4's table, band-bounded via the existing `all` combinator so only one threshold rule matches a given document at a time - a rule-authoring convention, not a code mechanism.
  - **Cross-document consistency checks (AC-FR-08-03: "V1 detects structured inconsistencies for product name, manufacturer, legal entity/address, shelf life and formula version") needed no new engine capability either, once framed correctly.** Comparing two *different* documents' fields against each other doesn't fit the engine's leaf model (a condition leaf compares one resolved field against a static literal, never against another field) - but C8's own entity catalog already defines "Consistency Check" as a distinct future entity ("Pair/set of normalized fields | Compared values, match policy, outcome, confidence and resulting finding"), meaning the actual field-matching computation belongs to that unbuilt C8 mechanism, not the C6 rule engine. So the caller supplies the already-computed comparison result as a fact (`consistency_checks[]`, `outcome` confidence-wrapped like everything else extraction-derived per C8's own field list), and a rule is just an ordinary `{"op": "equals", "field": "outcome", "value": "MISMATCH"}` check - zero new leaf operators.
  - **Routing `documents[]`-pool rules vs. `consistency_checks[]`-pool rules needed a real correctness fix, not just a convenience one.** A per-document rule (e.g. checking `expiry_date`) run against a `consistency_check` subject just resolves `UNKNOWN` on a missing field - if that rule's `unknown_behavior` is `FAIL_CLOSED`, it silently produces a bogus `NOT_SATISFIED`/proposed Finding attached to a subject it was never written for, and vice versa. Resolved via `RequirementVersion.subject_kind` (new column, see "Regulatory content: requirement / requirement_version" above) rather than an `obligation_type` string-prefix convention (`CONSISTENCY_`) that was considered and rejected - same reasoning as `StepRun.unknown_reason`: an explicit column, not an implicit string contract a rule author could forget. `_run_documents_dimension` splits active rules into `document_rules`/`consistency_rules` by `requirement_version.subject_kind` before evaluating either subject pool. Verified via weaken/confirm-fail/restore: merging both pools back together makes `tests/test_assessment_run_documents.py::test_consistency_and_document_requirements_route_to_correct_subject_pools` produce 4 `StepRun`s instead of 2.
  - **The AC-FR-06-02 low-confidence hard-pin generalizes to Documents automatically** (it lives in the dimension-agnostic engine/service layer, not Label-specific code) - confirmed explicitly rather than left as an unstated side effect: FR-08 relies on extracted data (issuer, dates, legal entity) the same way Label relies on OCR, so uncertain extraction shouldn't silently satisfy a mandatory check in either dimension.
  - **No `StepRun`/`RequirementResult`/`Finding`/`DimensionAssessmentState` changes needed for Documents.** `DOCUMENTS` was already a valid `RequirementDimension` value. FR-08's own document-lifecycle vocabulary (Missing/Uploaded/Processing/Review Required/Valid/Invalid/Expired/Expiring Soon/Superseded) stays out of `DimensionAssessment.state` - same precedent as Label's artwork-review states: it's per-document status expressed through facts/Findings, not the dimension-level rollup.

- **`requirement_result`** - C5.1's "future Requirement Result entity," referenced but deferred when `requirement_version` was first built (see that section above). No router - system-produced lineage data, same shape as `audit`'s `OutboxEvent`.
  - **One table serves both `APPLICABILITY`'s four-value vocabulary (`APPLIES`/`DOES_NOT_APPLY`/`UNKNOWN`/`CONFLICT`) and `REQUIREMENT_RESULT`'s satisfaction vocabulary (`SATISFIED`/`NOT_SATISFIED`/`UNKNOWN`)** - `outcome` stays a plain string column (this codebase's usual convention), but the service layer (`RequirementResultRepository.create_validated`) rejects any value outside the closed set matching whichever `RuleOutputType` produced it. Confirmed explicitly rather than splitting into two tables or leaving `REQUIREMENT_RESULT` outcomes as unstructured JSON.
  - **`CONFLICT` is accepted by the validator but never produced by the engine in this pass** - C5.1 defines it as a valid applicability outcome ("multiple rules disagree"), but detecting genuine multi-rule disagreement isn't built; each `APPLICABILITY` rule evaluation is independent, one `RequirementResult` row per (StepRun, RuleVersion). Flagged as a known gap, not silently unreachable-and-undocumented.
  - **`predicate_inputs` duplicates `StepRun.input_facts`** - deliberate, not an oversight: C5.1 frames the applicability decision itself as needing to "retain" its predicate inputs, read as the result being reconstructable without a join back to `StepRun`.
  - **`step_run_id`/`assessment_run_id` are both stored** (the latter derivable via the former) - same "duplicate a scoping FK for query convenience" precedent as `ProductVersion` carrying both `organization_id` and `product_id`.

- **`finding` / `finding_revision`** - implements C7. Org-scoped like `ProductMarketState` (customer-visible issue data); `require_manager` reads. **No write endpoints in this pass** - findings are only created by the engine (`FindingService.propose()`, called from `AssessmentRunService`), not by users; there's no RA-review workflow yet to drive status transitions via an API.
  - **`Finding` stays a thin, stable anchor; everything that changes per assessment lives on `FindingRevision`** - same Requirement/RequirementVersion split reasoning used throughout this codebase. One deliberate deviation from that precedent: `requirement_version_id`/`rule_version_id`/`subject_key` live on `Finding`, not `FindingRevision`, because they're part of what makes re-running an assessment recognize "the same issue" (`propose()`'s idempotent-reuse lookup keys on exactly this tuple) rather than spawning a duplicate `Finding` every run - a genuinely different rule/requirement/claim is a different `Finding`, not a new revision of one.
  - **`FindingRevision` is never updated in place - the one entity in this codebase where that's true.** C7 is explicit that the whole point of the Finding/FindingRevision split is keeping each assessment result immutable, so any change is a new row with the next `revision_number`, not a `setattr` loop.
  - **`propose()`'s re-run policy**: if the matching `Finding`'s latest revision is still `PROPOSED` (never reviewed), a re-run appends a fresh revision with current evidence. If a human has already acted on it (status moved past `PROPOSED`), a fresh automated detection is a no-op - the engine defers to human ownership once review has started, rather than silently resetting a reviewed finding back to `PROPOSED`.
  - **C7's "NO FREE-TEXT-ONLY FINDINGS" rule is only partially satisfied in this pass.** Severity/status/disposition-readiness (`hard_gate_effect`)/rationale are structured, required (`NOT NULL`) fields. The Recommendation group (`action_type`/`suggested_value`/`resolution_criteria`/`owner_user_id`/`due_date`) is **not populated** - `RuleVersion` has nowhere to source a structured action template from yet, and adding one (a new `output_template` field) was explicitly deferred rather than retrofitting an already-shipped model for this slice. Columns exist now (nullable) so a future template mechanism doesn't need a migration, but nothing writes to them today. AI lineage and Human lineage groups are omitted entirely (not even nullable columns) - no AI/RA-review layer exists yet to populate them, and unlike Recommendation there's no rule-authoring-time data that would need a column ready in advance.
  - **Severity reuses `RequirementSeverity` directly** (imported from `requirement_version.models`) - the second deliberate cross-module enum exception after `UnknownBehavior`, textually justified the same way: B4 states Finding severity is explicitly "inherited from the requirement," not an independently-defined vocabulary.

### Market readiness: `state_snapshot`, `market_readiness`

Implements FR-05/C1/B5 - the aggregator that runs-or-reuses each dimension's assessment and produces one overall gate for a `ProductMarketState`. Two new modules: `state_snapshot` (the `StateSnapshot` model + read-only endpoints, no write router - system-produced, same shape as `finding`) and `market_readiness` (the orchestration service + a single `POST /market-readiness-runs` endpoint). Small, additive-only changes to `assessment_run` (a public `run_dimension` wrapper around `_run_dimension`, two new `DimensionAssessmentRepository` queries) and one hook added to `ProductMarketStateService.update()` - nothing already-shipped changed shape.

- **`StateSnapshot` fields: only a subset of C1.1's seven field groups are real - and no dead placeholder columns exist for the rest.** Identity is fully real. Decision: `overall_gate`/`raw_progress`/`displayed_progress`/`readiness_reason_codes`/`outstanding_action_count` are real and computed; C1.1's `risk` field is deliberately **not** named `risk` here - it's `highest_open_severity`, the highest severity among this state's currently open Findings (or `null`), named for exactly what it computes rather than borrowing spec vocabulary ("risk") that implies a real risk-scoring model this codebase doesn't have. **`verification_state` and `configuration_hash` do not exist as columns at all** - same principle already applied elsewhere in this codebase (release membership, `impact_analysis_id`, `FindingRevision`'s AI/Human lineage groups): no Approval model exists to ever populate `verification_state` with anything but one fixed value, and no release-scoped engine configuration exists yet to meaningfully hash for `configuration_hash` - both get added when the layer that actually populates them exists, not reserved in advance as `null`/fixed-placeholder columns. Dimensions: `dimension_summary` is a self-contained JSON blob (`{dimension: {dimension_assessment_id, state, score, reused}}`), same "retain enough to reconstruct without a join" precedent as `RequirementResult.predicate_inputs`. Findings: `unresolved_severity_counts` is real; evidence sufficiency/evidence-link revisions deferred (no Evidence model, C8). Approvals: omitted entirely, not even nullable columns - same principle as above. Lineage: source/rule/requirement versions are derivable via `regulatory_basis_release_id` (not duplicated); document versions and model/prompt/parser versions deferred (no Document model, no AI layer); **`engine_build` is real, not a placeholder** - `get_settings().app_version`, the running application's own version, set once in `MarketReadinessService.__init__`. `impact_analysis_id` deferred (C11, unbuilt) - not a column either, same principle.
- **Reuse-vs-rerun (FR-05: "reusing valid current sub-assessments where safe") is keyed on `(product_version_id, regulatory_basis_release_id)` pins first, plus a submitted-facts content hash where there's anything to compare.** `DimensionAssessmentRepository.get_latest_reusable` finds the most recent `DimensionAssessment` for `(product_market_state, dimension)` whose originating run pinned the exact same product version and release and didn't `FAIL`. Two genuinely different reuse checks live in `MarketReadinessService._resolve_dimension`, not one:
    - **Dimension key absent from `input_facts`** - the caller submitted nothing this run for this dimension. Pins alone decide reuse; there's nothing submitted to compare against, so this path is unchanged from the original design.
    - **Dimension key present** - the caller resupplied this dimension's facts. `AssessmentRunService.hash_facts` (SHA-256 over the raw submitted dict, `sort_keys=True` - the same convention `StepRun.input_hash` already used) is computed and ANDed onto the same pin-scoped query via `DimensionAssessment.submitted_facts_hash`. Byte-identical resupply still reuses safely; genuinely different content falls through to a real rerun. `submitted_facts_hash` is deliberately **order-sensitive on lists** (no canonical sort before hashing) and **includes confidence values as-is** - a reordered `claims`/`label_fields`/`documents` list or a revised confidence-only correction both hash differently, forcing an occasional unnecessary rerun rather than risking a wrongly-skipped one; confidence is included because `AC-FR-06-02` already treats it as load-bearing content, not descriptive metadata. Floats are hashed via `json.dumps`'s own formatting, not rounded first - consistent with every other content-hash in this codebase (`StepRun.input_hash`, `RegulatoryBasisRelease.content_hash`, `InternalRoleAssignment.content_hash`), all of which carry the same latent, unaddressed float-representation-stability risk across Python/json versions.
    - **`submitted_facts_hash` is nullable, and pre-existing rows are never backfilled** - a true backfill is impossible, not just skipped: the raw submitted `dimension_facts` for a historical run was never persisted anywhere (only the derived per-step `StepRun.input_facts`, which is a different, less faithful quantity - see the "not derived from StepRuns" reasoning below). A `NULL` hash can never equal a freshly-computed one in SQL, so pre-migration rows simply keep reforcing a rerun on resupply forever, with no special-casing needed - the exact behavior they had before this column existed.
    - **Deliberately NOT derived from `StepRun.input_facts`** - `StepRun.input_hash` is scoped to one rule's *resolved* per-subject view (subject facts merged with product facts, sometimes reshaped, e.g. Label's `_build_label_field_facts` nesting under `"extracted"`), not the caller's raw submission. A field submitted but unreferenced by any active rule's condition would be invisible to a StepRun-derived hash, under-detecting real changes; and five of eight canonical dimensions have zero active rules today, producing zero `StepRun`s - a StepRun-derived hash would be undefined exactly where the unbuilt dimensions matter most. `DimensionAssessment.submitted_facts_hash` hashes the whole raw `dimension_facts` dict directly, computed once in `AssessmentRunService._run_dimension`, independent of what any rule happened to read.
  - **Supplying a dimension's key in `input_facts` at all - even an empty dict - is still the outer gate that routes into the hash-comparison branch above**, not itself sufficient to force a rerun anymore. Checked by key presence (`set(payload.input_facts.keys())`), not value truthiness, to avoid the ambiguity of "empty but present" collapsing into "key absent" - the hash comparison only ever narrows an already-triggered rerun path into a safe reuse when content is identical, it never widens the key-absent path.
  - **Market Readiness attempts all eight canonical `RequirementDimension` values every run**, not just the three with real rule content (`SUPPORTED_DIMENSIONS` on `AssessmentRunService` stays unchanged, still gating the standalone `POST /assessment-runs` endpoint). A dimension with zero rule content naturally settles at `DimensionAssessmentState.UNKNOWN` (`_derive_dimension_state`'s own `if not steps: return UNKNOWN`, unchanged) - this is exactly the signal G0's "required dimension Unknown" gate condition needs, not a reason to special-case anything. A dimension that DOES have rule content but resolves zero subjects from what was submitted settles at the distinct `NO_SUBJECTS_RESOLVED` instead (see "Assessment engine" above) - the two are no longer conflated. `AssessmentRunService.run_dimension` is the new public entrypoint that makes this possible - it bypasses `create_and_run`'s `SUPPORTED_DIMENSIONS` validation deliberately, since Market Readiness is a trusted internal orchestrator, not a direct single-dimension caller.
- **Gate calculation (B5.3), resolved explicitly at each fork, not left to inference alone**:
  - **`NO_SUBJECTS_RESOLVED` blocks at G0 alongside `UNKNOWN`, with its own `DIMENSION_NO_SUBJECTS_RESOLVED` reason code, never merged into `DIMENSION_UNKNOWN`.** Both mean "no opinion could be formed for this dimension at all" - a different, earlier kind of gap than G1's "an opinion was formed and it's blocking" - so both stay in the same G0 bucket the way `critical_open`/`hard_gate_open`/`non_compliant` already share G1 with distinct reason codes each.
  - **Non-dispositioned Finding statuses block the gate, not literally `status == "OPEN"`.** `_CLOSED_FINDING_STATUSES` (`RESOLVED`/`ACCEPTED_WITH_RATIONALE`/`NOT_APPLICABLE`/`REJECTED`/`SUPERSEDED` — now an alias for `finding.models.TERMINAL_FINDING_STATUSES`, see "Finding review workflow" below) is the actual boundary; everything else (`PROPOSED`, `OPEN`, `CUSTOMER_RESPONDED`) blocks. This logic was written generically against the full 8-value `FindingStatus` vocabulary from the start, even back when `FindingService.propose()` was the only write path and nothing ever transitioned a Finding past `PROPOSED` — gating strictly on `"OPEN"` would have made G1 permanently unreachable, which can't be AC-FR-05-02's intent. Now that the Finding review workflow lets findings actually reach `_CLOSED_FINDING_STATUSES`, this code needed zero changes to start reflecting real dispositions — it was already forward-compatible with transitions that didn't exist yet.
  - **An open Finding with `hard_gate_effect=True` forces G1 on its own, independent of severity** — B5.3's G1 condition ("any open Critical finding, explicit ineligibility or **non-compliant blocking rule**") names three separate triggers, not one restated three ways, and C5/C7 both list hard-gate status and severity as distinct fields in two independent places (C5's Risk group: "default severity, hard-gate flag..."; C7's Decision group: "severity, status, disposition, hard-gate effect..."), never one derived from the other. `_open_findings` carries `hard_gate_effect` alongside `severity`/`status` per open Finding; `_compute_gate`'s new `hard_gate_open` check is OR'd into the same G1 branch as `critical_open`, with its own `HARD_GATE_FINDING_OPEN` reason code so it's never confused with the severity-based trigger. Deliberately additive, not a replacement: a Critical finding with `hard_gate_effect=False` still forces G1 on the severity path alone, and a Moderate/Minor/Informational finding with `hard_gate_effect=True` now also forces G1 on its own — verified via weaken/confirm-fail/restore and three dedicated tests (`test_compute_gate_open_hard_gate_finding_forces_g1_regardless_of_severity`, `test_compute_gate_moderate_finding_without_hard_gate_does_not_force_g1`, `test_compute_gate_critical_without_hard_gate_still_forces_g1`). `_build_snapshot`'s severity counting (`unresolved_severity_counts`/`highest_open_severity`) is untouched by this — it stays purely severity-keyed, so a hard-gate-triggered G1 can legitimately appear alongside a non-Critical `highest_open_severity`; `readiness_reason_codes` (via `HARD_GATE_FINDING_OPEN`) is what explains that combination, not a severity-count change. No existing test needed to change — confirmed directly that no test anywhere exercised `_compute_gate` with an open Finding of any kind before this (`test_market_readiness.py`'s own rules never used `FINDING_PROPOSAL`, and the three `assessment_run` test files that do never touch Market Readiness at all).
  - **G3 maps onto `DimensionAssessmentState.HUMAN_REVIEW_REQUIRED`** - flagged as inferred, not a literal reading: G3's own wording ("required decisions remain AI-only or confidence/approval policy is unmet") describes an AI/RA-review concept this codebase doesn't have a direct analog for; `HUMAN_REVIEW_REQUIRED` is the closest existing signal.
  - **G4 and G5 are permanently unreachable this pass, by explicit decision, not by accident** - "absence of approval infrastructure is not approval." Whatever would otherwise satisfy G4 (every dimension compliant, no open Critical/Major findings) is capped at G3 instead, with a distinct reason code (`G4_UNREACHABLE_NO_APPROVAL_MODEL`) so it's never confused with a genuine `HUMAN_REVIEW_REQUIRED` G3. Verified via weaken/confirm-fail/restore against `test_compute_gate_g4_and_g5_are_unreachable_even_when_all_conditions_met`. G5 needs real Authority Event data (Execution bounded context, entirely unbuilt) and was never in scope.
  - **`_dimension_score` (B5.2) groups `RequirementResult` rows by `requirement_version_id` before scoring, not per-row** - the same `RequirementVersion` can have both an `APPLICABILITY` row and a `REQUIREMENT_RESULT` row (two different `RuleVersion`s), and each must contribute its `importance_weight` exactly once, or the denominator double-counts it. Verified via weaken/confirm-fail/restore (`test_dimension_score_avoids_double_counting_and_applies_alone_scores_zero` catches a per-row-instead-of-per-requirement regression precisely). **`APPLIES` alone (no accompanying `REQUIREMENT_RESULT` outcome for the same requirement) scores 0.00, not 1.00** - applicability establishes relevance, not satisfaction; scoring it as compliant would overstate readiness for a requirement nothing has actually verified. Only 3 of B5.2's 6 progress-factor rows are reachable without the unbuilt AI/RA-review layer (`SATISFIED` -> 1.00, Not Applicable -> Excluded, everything else -> 0.00) - same "6 of 12 B3 states reachable" pattern as `DimensionAssessmentState` itself. **A `RequirementVersion` enforced purely via `FINDING_PROPOSAL` rules never produces a `RequirementResult` row at all** (that output type writes only a `Finding`), so it never contributes to a dimension's weighted score - a real, known gap, not a silent one.
  - **Not-Applicable exclusion (B5.2's "Not Applicable requirements are excluded from the denominator") is extended to whole dimensions too** - B3's own Not-Applicable definition explicitly names "the dimension/requirement," so a `NOT_APPLICABLE` `DimensionAssessment` drops out of both the numerator and denominator of the B5.1 overall-progress weighted average, the same way an excluded requirement does within a dimension. An `UNKNOWN` (unbuilt) dimension is **not** excluded this way - it's scored 0.00 with its full portfolio weight retained, which is what makes the "unbuilt dimensions correctly cap displayed progress at 49% via G0" mechanism work without any special-casing.
- **FR-05's own state list ("Preflight Failed -> Queued -> Assessing -> AI Assessed -> RA Review -> Customer Action / RegNova Verified / Not Ready -> Ready for Registration") gets no fourth persisted enum** - resolved explicitly against the precedent that every other FR/B state list built so far (`AssessmentRunStatus`, `DimensionAssessmentState`, `FindingStatus`, `ProductMarketStateGate`) got its own vocabulary. Composed instead from the three that already exist: Preflight Failed = `MarketReadinessPreflightFailed` raised before any `AssessmentRun` row is even created; Queued/Assessing = `AssessmentRunStatus.QUEUED`/`RUNNING` (unchanged); AI Assessed/RA Review = unreachable, no AI/RA layer; Customer Action Required/Not Ready/Ready for Registration = gate values G2/G1/G4 (G4 itself currently unreachable, see above); RegNova Verified has no gate equivalent (it's a B3 dimension state, `DimensionAssessmentState` doesn't include it either - one of the 6-of-12 unreached states).
- **Preflight is its own step, returning every unmet prerequisite, not raising on the first.** `MarketReadinessService.run_preflight` checks: product version pinned (`NO_PRODUCT_VERSION`); pinned version published, resolved against **`ProductVersion.released_at`, not `ProductVersionStatus`** (`PRODUCT_VERSION_NOT_PUBLISHED`) - these two lifecycles aren't reconciled (an already-logged gap), and `released_at` is the more literal reading of "published"; regulatory basis pinned (`NO_REGULATORY_BASIS`); pinned release genuinely `ACTIVE`, not just present - **a real strengthening over `AssessmentRunService.create_and_run`'s own check**, which only tests `regulatory_basis_release_id is not None` and never re-validates the referenced release's own status (`REGULATORY_BASIS_NOT_ACTIVE`). **Required intake fields are deliberately not checked** - no such checklist is modeled anywhere in this codebase (Product/ProductVersion has no "required intake fields" concept at all); documented as unbuilt rather than inventing a synthetic field list. The shared `AppException`/global-handler contract only ever serializes one `message` string (see `app/common/handlers.py` - it builds the JSON body from `exc.error_code`/`exc.message` directly, ignoring `to_dict()`), so `MarketReadinessPreflightFailed` joins every failure into that one message rather than extending the shared envelope for one feature; the full structured list is still available as `.failures` on the exception instance. Verified this actually reports everything, not just the first match, via `test_preflight_reports_all_failures_not_just_first`.
- **Staleness has two deliberately separate halves, both in scope; cascading impact analysis stays out.** (1) Whenever `MarketReadinessService._build_snapshot` creates a new `StateSnapshot`, the previous current one for that `ProductMarketState` is marked `is_current=False`, `stale_reason="SUPERSEDED_BY_NEW_SNAPSHOT"`, `superseded_by_snapshot_id=<new id>`. (2) `ProductMarketStateService.update()` marks the current snapshot stale **synchronously, in the same transaction**, the moment `product_version_id`/`regulatory_basis_release_id` actually changes (`stale_reason="PRODUCT_MARKET_STATE_PIN_CHANGED"`) - via `StateSnapshotRepository` directly, not by importing `MarketReadinessService` (which would pull in `AssessmentRunService`/`FindingService`/etc. just to flag one row, and would invert the natural module-layering direction). **Out of scope, explicitly**: C11's cascading impact analysis - walking dependency edges to figure out exactly which Requirement Results/Findings are affected by a specific changed fact (`impact_analysis_id`, deferred per the StateSnapshot fields note above). This mechanism only ever says *that* a snapshot is stale, never *why* in that structural detail.

### Internal role model: `internal_role_assignment`, `Organization.is_internal`, `User.is_permanent_admin`

Implements A4/B2/FR-13's internal-actor governance: how RegNova's own staff (RA, Senior Reviewer, Submission Operations, Platform Admin, Regulatory Knowledge Lead) are represented as structurally distinct from customer-org users, how they get granted a role, and how that finally replaces the `require_admin` placeholder that gated `source`/`requirement`/`rule`/`regulatory_basis_release` writes. Leadership-approved design, not speculative — proposed, resolved, and implemented in one pass; see `tests/test_internal_role_assignment.py` for the behavioral guarantees below.

- **"Tenant zero" pattern, not a new actor-type concept.** `Organization.is_internal: bool` (DB-only settable — no Create/Update schema field, ever) marks exactly one organization as RegNova itself (`uq_organizations_single_internal`, a partial unique index, enforces "exactly one" at the DB level). RegNova staff are ordinary `User` rows in that org, reusing every existing auth/JWT/RBAC mechanism as-is — no new token shape, no new login path. **Explicitly scoped**: this buys identity/login/internal-role-checking only, *not* cross-tenant data visibility — every existing org-scoped repository still filters strictly by `current_user.organization_id`, so an RA's own `organization_id` (tenant-zero's) never matches a customer's data under any existing query. Acting-as-a-specific-customer-org (the audited scope-switch an "RA Workbench" would need) is out of scope for this pass, per explicit instruction, and needs its own design.
- **Internal roles are a second, orthogonal axis of authority from `Role`/`role_id` — not reused from it, on purpose.** `Role` is org-scoped, ordered (Employee ⊆ Manager ⊆ Admin), and `User.role_id` is a single FK: one role at a time, from one tier. RA/Senior Reviewer/Submission Operations/Platform Admin/Regulatory Knowledge Lead aren't a tier of each other and (per B2) a person could plausibly need more than one — that shape doesn't fit `Role` at all, hence a new `InternalRoleAssignment` table rather than adding role codes to the existing enum. `InternalRoleCode` (`RA`/`SENIOR_REVIEWER`/`SUBMISSION_OPERATIONS`/`PLATFORM_ADMIN`/`REGULATORY_KNOWLEDGE_LEAD`) is a plain string column, not a shared enum reused elsewhere.
  - **`REGULATORY_KNOWLEDGE_LEAD` is its own fifth role code, not a scope on `PLATFORM_ADMIN`** — an explicit resolution, not an inference: A4 draws a hard line ("Platform administrator... Cannot alter regulatory decisions without a regulated role"), and FR-13 lists "Regulatory Knowledge Lead, authorized RA reviewer, platform admin (technical only)" as three separate actors. Modeling regulatory-content authority as a *scope* on the most access-restricted role would invert that boundary — the most sensitive capability riding on the most locked-down role, gated by a JSON list nothing validates against a closed vocabulary. `scope` on `InternalRoleAssignment` stays a `PLATFORM_ADMIN`-only technical qualifier (infrastructure/security/config areas) — an extensible open list, not hardcoded to two values, but no concrete scope value is exercised by any check in this pass.
  - **`require_regulatory_content_writer` checks `REGULATORY_KNOWLEDGE_LEAD` only** — deliberately not RA/Senior Reviewer too, even though FR-13's Graph Console actor line also names "authorized RA reviewer." B2's own permission table gives RA/Senior Reviewer authority over assessment-side data (findings, review decisions), not regulatory-content authoring, which FR-13 frames as the Knowledge Lead's specific responsibility.
- **Propose (HR) / decide (CEO) is two genuinely separate persisted writes on one row's lifecycle** (`PROPOSED` → `APPROVED`/`REJECTED`), reusing this codebase's own established versioned-entity pattern (`RequirementVersion`/`RuleVersion`/`SourceVersion`: created in one state, transitioned by a separate later write) rather than a new two-table design. `InternalRoleAssignment`'s field shape reuses D6.1's Approval-object vocabulary narrowly (approver identity, decision, rationale, timestamp, expiry/revocation behavior, content hash) — not a generic polymorphic Approval entity covering all of D6's approval matrix, which is separate, larger, future scope.
  - **`content_hash`** — SHA-256 over `{user_id, role_code, scope}` at proposal time, same style as `AssessmentRunService`'s `StepRun.input_hash` and `RegulatoryBasisRelease.content_hash`. There is no edit path for those three fields after creation (a scope/role change always creates a new row — see supersession below), so today it's a real, computed, stored integrity marker with no exercised edit-detection path yet, not a placeholder.
  - **`POST /internal-role-assignments` (propose) is still gated by `require_admin`, and this is a known, explicitly-flagged placeholder** — no "HR" actor-type exists in RBAC. The service layer separately and unconditionally requires the proposer to actually be tenant-zero staff (`_require_internal_user`), so an ordinary customer-org admin passes the router-level check but is rejected by the service with `TargetUserNotInternal` (400) — `require_admin` alone never grants the ability to propose an internal role. `GET`s on this module are `require_admin` too, for the same "no finer actor-type exists yet" reason — reads aren't sensitive the way propose/decide are, so this one is lower-priority to resolve.
  - **`decide`/`decide-revocation`/`revoke` are gated by `require_ceo`**, a *different kind* of dependency from every other `require_*` in this codebase — it checks one specific account (`current_user.is_permanent_admin is True`), not a role tier. `RBACService.require_role` was not reused here; `require_ceo` is a standalone check.
- **"No customer-side account can ever hold an internal role" is enforced once, structurally, in `propose()` — not left to caller discipline.** `_require_internal_user(user_id)` validates the *target* belongs to tenant-zero the same way it validates the *proposer* does; both raise `TargetUserNotInternal` (400) on a customer-org id. This is the single write path that creates `InternalRoleAssignment` rows, so there is no other route to a customer-org id ending up in `user_id` here. Verified via weaken/confirm-fail/restore (`tests/test_internal_role_assignment.py::test_propose_rejects_customer_org_proposer`/`::test_propose_rejects_customer_org_target`) and covered from both the proposer side and the target side, since they're independent checks.
- **`User.is_permanent_admin` ("the CEO seat") is DB-only settable, forever, by design — there is deliberately no API path to set OR transfer it**, not even for the account itself. `UserService.update()`/`delete()` both refuse unconditionally whenever the target has `is_permanent_admin=True` and the request would change `role_id`, set `is_active=False`, or delete the row at all — refused for *any* caller, including another ADMIN and including the CEO's own request, via `PermanentAdminProtected` (409). This is a structural check on one specific row, not a role-tier permission check — same asymmetry as `require_ceo` vs. `require_admin`. Verified via weaken/confirm-fail/restore, one check at a time (`tests/test_internal_role_assignment.py::test_ceo_resists_role_change_from_another_admin`/`::test_ceo_resists_deactivation_from_another_admin`/`::test_ceo_resists_deletion_from_another_admin`). **Known limitation, deliberate**: no succession path exists — an endpoint able to transfer permanent-admin status would defeat the whole point of the flag being unforgeable through the API. See "Known limitations" below.
- **Revocation reuses the same propose/approve shape as the grant itself, except the CEO may bypass it entirely.** `propose_revocation()`/`decide_revocation()` mirror `propose()`/`decide()` (a pending revocation proposal on an `APPROVED` row, decided by the CEO into `REVOKED` or cleared back to a clean `APPROVED` state) — for the ordinary case where someone other than the CEO needs to initiate it. `revoke()` is a separate, CEO-only unilateral action (`require_ceo`) that goes straight from `APPROVED` to `REVOKED`, bypassing the propose/decide pair entirely — "the same flow, except the CEO who may revoke unilaterally" was an explicit resolution, not an oversight that two revocation paths exist.
- **A scope or role change is always a new row via `propose()` again — never an edit to the existing one.** *Proposing* a change must never suspend existing access: the old row stays `APPROVED` for the entire `PROPOSED` window of the new one. Only once the new row is actually **approved** does `_supersede_prior_approved` flip the old row to `SUPERSEDED` (with `superseded_by_id` set) — matched against the same `(user_id, role_code)`, looked up via `InternalRoleAssignmentRepository.get_active_for_user_role`. This means there is never a moment with either zero or two simultaneously-`APPROVED` rows for the same `(user, role_code)`. The "only fires on approval, not on propose" timing is the single most fragile invariant in this module — verified via weaken/confirm-fail/restore (moving the `_supersede_prior_approved` call into `propose()` makes `tests/test_internal_role_assignment.py::test_pending_scope_change_proposal_does_not_suspend_existing_grant` fail exactly as expected, restored after confirming). The same "proposing never suspends" principle applies to `propose_revocation()` — it only sets the pending-revocation fields, `status` stays `APPROVED` until actually decided.
- **`expires_at` exists as a column, unused this pass** — D6.1's "expiry... behavior" field, deferred rather than reserved silently: nothing sets or checks it yet, flagged the same way `RuleVersion.test_fixtures`' execution engine and `FindingRevision`'s Recommendation group are flagged elsewhere in this file.

### Finding review workflow: `FindingService` transitions

Implements B4's Finding status vocabulary as a real state machine. Before this, `FindingService.propose()` was the only write path and only ever wrote `PROPOSED` — nothing transitioned a Finding further, which is why `market_readiness`'s gate had to treat every non-terminal status as equally blocking. Scoped and built in one pass (propose → resolve → implement), see `tests/test_finding_review.py` for the behavioral guarantees below.

- **Eight `FindingStatus` values split cleanly into `NON_TERMINAL_FINDING_STATUSES` (`PROPOSED`/`OPEN`/`CUSTOMER_RESPONDED`) and `TERMINAL_FINDING_STATUSES`** (`RESOLVED`/`ACCEPTED_WITH_RATIONALE`/`NOT_APPLICABLE`/`REJECTED`/`SUPERSEDED`) — both defined once in `finding/models.py`, exact complements of each other. `market_readiness/service.py`'s own gate-blocking set (`_CLOSED_FINDING_STATUSES`) is now an alias for `TERMINAL_FINDING_STATUSES` rather than a second, independently-maintained literal — the two concepts (gate-blocking, transition-legality) turned out to be the same set viewed from two services, so keeping one definition was a deliberate consolidation, not a coincidence worth ignoring.
- **`PROPOSED` is not a mandatory single-hop waypoint** — an explicit resolution, not a spec-literal reading: `resolve()` and `accept_with_rationale()` both accept any `NON_TERMINAL` starting status (`PROPOSED`, `OPEN`, or `CUSTOMER_RESPONDED`), so a finding can go straight from freshly-proposed to a terminal disposition in one transition when that's the real shape of what happened, rather than forcing a synthetic intermediate `OPEN` hop.
- **Seven named transition methods, not one generic status-setter** — `accept`/`reject`/`mark_not_applicable`/`respond`/`reopen`/`resolve`/`accept_with_rationale`, mirroring this codebase's existing named-action precedent (`InternalRoleAssignmentService.propose`/`decide`/`revoke`, `ProductVersionService.publish`) over a generic `PUT status=X`. Each is a fixed, hardcoded (from-status, target-status, required-actor) triple — deliberately not a table keyed by target-status alone, because the same target status can require different actors depending on where it's coming from: `PROPOSED → OPEN` (`accept()`) is customer-or-RA triage, but `CUSTOMER_RESPONDED → OPEN` (`reopen()`) is RA/Senior-only (the response was reviewed and judged insufficient) — collapsing these into one "target == OPEN" check would have silently let a customer reopen their own case.
- **Every transition appends a new `FindingRevision`, never mutates one** — copies the prior revision's observation fields (`issue_type`/`observed_value`/`normalized_value`/`observed_location`/`severity`/`hard_gate_effect`) and its `source_locations` forward unchanged (mechanically required anyway: `issue_type`/`observed_value` are `NOT NULL`), writing only the new decision fields. Same immutability contract C7 already established for engine-driven revisions, now proven to hold for human-driven ones too.
- **`FindingRevision.decided_by_user_id` is new** — C7's "Human lineage" field group (reviewer, reason, approval, timestamps) was entirely absent from this model before this pass; this is the one field it actually needed. No separate `decided_at` — a transition-creates-a-revision model means `created_at` (`TimestampMixin`) already stamps that moment.
- **Authorization lives entirely in the service, not as a router-level `require_*` dependency** — a deliberate, explicit resolution, not a shortcut. Every transition endpoint is gated only by `get_current_active_user` (bare authentication); `FindingService` itself checks whether the specific actor is authorized for the specific transition against the specific finding. This is necessary, not just tidier: `RESOLVED`'s required actor depends on the finding's own current `severity`, which the router has no way to know before the service loads the finding — a static per-route dependency literally cannot express this check. Two independent authorization axes, checked directly rather than through existing `require_*` dependencies (which check one axis each and can't be ORed together at the router):
  - **Customer-side**: `RBACService.require_role(db, actor, "ADMIN", "MANAGER")`, called against the *actor's own* org — meaningful because by the time this runs, `get_by_id`'s org-scoped lookup has already established `actor.organization_id == finding.organization_id`. Maps B2's "Resolve findings: Yes" (Organisation admin, Customer regulatory lead) onto this codebase's existing ADMIN/MANAGER role tier — the same tier the GET endpoints on this router already require. B2's "Assigned" grant for Contributor isn't modeled (no per-finding assignment mechanism exists), so Contributor-level access isn't distinguished from Viewer here.
  - **RA-side**: `InternalRoleAssignmentRepository.get_active_for_user_role(actor_user_id, "RA"/"SENIOR_REVIEWER")` — completely independent of the actor's own organization, by design; this is structurally the same authority an eventual RA Workbench would formalize, just not reachable yet (see below).
- **The full transition/actor table, resolved explicitly rather than inferred from a single spec line**:

  | Transition | From → To | Actor |
  |---|---|---|
  | `accept()` | `PROPOSED → OPEN` | Customer manager **or** RA/Senior |
  | `reject()` | `PROPOSED → REJECTED` | RA/Senior only — B4 frames rejection as correcting the engine's own proposal ("becomes evaluation data", D10.3), not a customer dispute mechanism |
  | `mark_not_applicable()` | `PROPOSED → NOT_APPLICABLE` | RA/Senior only — a regulatory-applicability judgment, same weight as C5.1's Does Not Apply |
  | `respond()` | `OPEN → CUSTOMER_RESPONDED` | Customer manager only |
  | `reopen()` | `CUSTOMER_RESPONDED → OPEN` | RA/Senior only |
  | `resolve()` | any `NON_TERMINAL → RESOLVED` | **Severity-gated**: Critical → Senior Reviewer only; Major → RA or Senior; Moderate/Minor/Informational → customer manager or RA/Senior |
  | `accept_with_rationale()` | any `NON_TERMINAL → ACCEPTED_WITH_RATIONALE` | RA/Senior only, **regardless of severity** — B4 says "approved by authorized RA" with no severity carve-out the way `RESOLVED` gets one |

  `SUPERSEDED` has no transition into it at all this pass — see below.
- **Critical-severity enforcement is structurally guaranteed, not weakened for testability** — a customer manager attempting `resolve()` on a Critical or Major finding gets `FindingTransitionNotAuthorized` (403) every time; this was verified via weaken/confirm-fail/restore (temporarily letting ordinary RA satisfy the Critical branch made `test_ra_alone_cannot_resolve_critical_finding_via_service` fail exactly as expected, restored after confirming). No fallback exists that lets a Critical finding reach `RESOLVED` without a genuine Senior Reviewer.
- **RA/Senior-only leaves are real, tested logic — and simultaneously unreachable via HTTP, on purpose, not by omission.** `FindingService.get_by_id()` is org-scoped to the *caller's* `organization_id`; an RA/Senior actor's own org is always tenant-zero, which can never equal a customer's Finding.organization_id, so the router-level lookup 404s before authorization is ever reached — the exact same tenant-isolation boundary `internal_role_assignment` already established, not a new restriction invented here. `tests/test_finding_review.py` proves both halves explicitly: the RA-only service methods are called *directly* (bypassing the router, passing the finding's real organization_id) to prove the authorization logic itself is correct, and a separate test (`test_ra_cannot_reach_finding_via_http_cross_org`) proves the same RA genuinely gets a 404 through the actual HTTP path. This mirrors the already-logged "RA Workbench acting-as-organization" gap exactly — closing it is out of scope here, same as it was for the internal role model.
- **`SUPERSEDED` gets no automated trigger this pass — deliberately out of scope, not forgotten.** B4: "a newer finding replaces it after version or rule change." `superseding_finding_id` already exists as a column, but detecting "this Finding's requirement/rule is no longer current" is C11's change-event/impact-propagation machinery, which this codebase has documented as unbuilt since before this ticket. `SUPERSEDED` stays a valid enum value with no code path that writes it.
- **`disposition` stays an open string, no fixed vocabulary** — same "needs real definition before constraining" treatment already applied to `obligation_type`/`verification_level` elsewhere in this codebase. Every transition method accepts it as an optional free-text field; nothing validates its contents against a closed set.

## Regulatory content decisions (not yet reflected in code)

No `document`/`documents` module exists yet (C8.1's extraction schemas aren't implemented), so these are recorded here for whoever builds it, confirmed against real NPRA requirements via web research on 2026-08-11:

- **Add "Safety Assessment Report" as an eighth C8.1 extraction schema** (originally seven: Formula/INCI, Artwork, GMP certificate, CFS, COA, Stability report, LOA). NPRA's PIF guideline (Annex I, Part 13) and its dedicated Safety Assessment guideline (Annex I, Part 6) both require this as a distinct document. Required normalized fields: product/formula version, safety assessor identity/qualification, toxicological endpoints assessed, exposure calculation, conclusion, assessment date.

### Request flow

`router.py` → FastAPI `Depends` chain resolves a `Session` (`app/core/dependencies.py:get_db_session`, one session per request, pulled from `request.app.state.database.session_factory`) → a `Service` instance → the service uses a `Repository` for queries and owns the commit/rollback. Errors are raised as `AppException` subclasses (`app/common/exceptions.py`) and turned into a uniform JSON error body by the global handler registered in `app/common/handlers.py` (`{"success": false, "error": {"code", "message"}}`). Routers do NOT catch `AppException` themselves — only a couple of legacy routes still catch bare `ValueError` and re-raise as `HTTPException` (see `organization/router.py`); new code should just let `AppException` subclasses propagate.

### Domain events / outbox

State-changing actions publish schema-versioned domain events through a transactional outbox (`app/modules/audit/`), per the RegNova spec's C14 event/audit contract.

- Every event-emitting service builds an `OutboxRepository(db)` alongside its own repository (same shape as `product_version`'s `self.products = ProductRepository(db)`) and calls `self.outbox.append(...)` **before** its own `self.db.commit()` — never a separate commit. The outbox row and the domain write land in the exact same transaction; that's the whole transactional guarantee, and it falls out of this codebase's existing "repositories flush, services commit once" convention rather than needing new plumbing.
- `correlation_id` and `actor_user_id` are threaded as explicit optional keyword arguments into the specific service methods that emit events (not baked into service `__init__`), sourced from `Depends(get_correlation_id)` and `current_user.id` in the router handler — matching the existing convention of passing context (like `organization_id`) explicitly into service methods rather than stashing it on the instance.
- `CorrelationIdMiddleware` (`app/core/correlation.py`) reads/generates `X-Correlation-Id` per request onto `request.state`; `get_correlation_id` (`app/core/dependencies.py`) is the FastAPI dependency that exposes it to routers.
- `OutboxRepository.get_unpublished()` applies `FOR UPDATE SKIP LOCKED` only when the session's dialect is `postgresql` — that's a Postgres-only concurrent-claim guarantee, not something meaningfully testable against the SQLite database the test suite runs on (SQLite silently no-ops `with_for_update()` rather than erroring, but relying on that silently would be fragile).
- `app/modules/audit/worker.py:dispatch_pending_events()` is the dispatcher — a plain function, not auto-started anywhere (no background loop wired into `lifespan()`). It's meant to be invoked by a scheduler/worker process. The actual dispatch transport (queue/bus/etc.) is deliberately not chosen yet — it logs the event — pending the durable-work architecture spike the spec (A5.1) calls for.
- First three events wired up so far: `WorkspaceActivated` (`OrganizationService.create()`), `MembershipChanged` (`UserService.create()`/`update()` when `role_id`/`is_active` change/`delete()` — **not** `RoleService`, since Appendix 2 describes membership/assignment changes, not `Role`-entity-definition edits — open question logged for RegNova product-side clarification if that's wrong), `ProductVersionPublished` (`ProductVersionService.publish()`, a dedicated method/endpoint — not folded into the generic `update()`; see the Known Limitations note below on why).

### Multi-tenancy pattern

`Organization` is the tenant root (`app/modules/organization/models.py`). Entities scoped to an org (`User`, `Role`, `Product`) carry an `organization_id` FK and their repositories require `organization_id` as an explicit argument on lookups (see `UserRepository.get_by_id(organization_id, user_id)`, `get_all(organization_id)`) — this is how tenant isolation is enforced, there is no automatic row-level filtering. When adding a new org-scoped entity, follow this same explicit-`organization_id`-parameter convention rather than relying on `BaseRepository`'s plain `get_by_id(entity_id)`. `Organization` itself and other non-scoped lookups use `BaseRepository`'s methods directly.

### Auth & RBAC

- JWT access/refresh tokens (`app/modules/auth/jwt.py`, HS256 via `settings.secret_key`). Access tokens embed `organization_id` and `role_id` as custom claims.
- `get_current_user`/`get_current_active_user` (`app/modules/auth/dependencies.py`) decode the bearer token and load the `User` scoped by `organization_id` from the token — a token cannot be used to fetch a user from a different org.
- RBAC is role-code based, not a permissions table: `app/modules/rbac/service.py:RBACService.require_role(db, user, *role_codes)` loads the user's `Role` and checks `role.code.upper() in role_codes`. `app/modules/rbac/dependencies.py` exposes ready-made FastAPI dependencies `require_admin` / `require_manager` / `require_employee` (each a superset of the next, e.g. `require_manager` accepts `ADMIN` or `MANAGER`) — use these in router signatures rather than calling `RBACService` directly.
- `app/modules/rbac/permissions.py` defines a `Permission` enum (`organization:read`, `user:write`, etc.) but nothing currently consumes it — the enforcement path in use today is role-code based (`require_admin` etc.), not permission-based.
- `require_ceo` / `require_ra` / `require_senior_reviewer` / `require_submission_operations` / `require_platform_admin` / `require_regulatory_content_writer` (also in `app/modules/rbac/dependencies.py`) are a **second, unrelated axis** from `require_admin`/`require_manager`/`require_employee` — they check `User.is_permanent_admin` or an approved `InternalRoleAssignment`, not `Role`/`role_id`. See "Internal role model" below for why these needed a separate mechanism rather than extending `Role`.

### Shared building blocks

- `app/shared/mixins/`: `UUIDMixin` (UUID PK, `default=uuid.uuid4`), `TimestampMixin` (`created_at`/`updated_at` with `server_default=func.now()`). Every model inherits both.
- `app/common/repository.py:BaseRepository` — generic `get_all`/`get_by_id`/`create`/`update`/`refresh`/`delete`. `create`/`update` call `flush()`+`refresh()` but not `commit()` — committing is the service layer's job.
- `app/common/exceptions.py` — base `AppException` plus `NotFoundException` (404), `ConflictException` (409), `ValidationException` (400), `AuthenticationException` (401), `AuthorizationException` (403). Module exceptions subclass these (e.g. `OrganizationNotFound(NotFoundException)`), matching FastAPI status codes to the base class.
- `app/common/responses.py:ApiResponse[T]` — a generic response envelope; not currently wired into routers (routers return response-model schemas or plain dicts directly).

## Security

- **`organization_id` must always be derived from `current_user.organization_id`, never accepted as a query or body parameter from the client.** Every org-scoped route must depend on `get_current_active_user` (directly or via `require_admin`/`require_manager`/`require_employee`) and pass `current_user.organization_id` into the service call — do not add `organization_id: UUID` as a router function parameter. This applies to every org-scoped module (`product`, `product_version`, `role`, `user`). Accepting it from the request lets an authenticated caller from one org read or write another org's data (cross-tenant IDOR) simply by passing a different `organization_id`.
- **Any other foreign key crossing into another resource must be validated against the caller's org too, not just `organization_id` itself.** `product_version`'s service resolves `product_id` through the `product` module's own org-scoped repository before touching anything else — don't trust a path/body id just because the surrounding request is authenticated.

## Known limitations / revisit later

- **`product_version`'s "current version" is a computed query** (`ProductVersionRepository.get_current`: most recent `is_active` version with `status == APPROVED`, ordered by `created_at`), not a stored pointer. This will likely need revisiting once multi-market versions exist (e.g. "current version for region X" isn't expressible as a single global ordering anymore).
- **`product_version` `status` transitions (`DRAFT`/`IN_REVIEW`/`APPROVED`/`ARCHIVED` via `update()`) still have no audit trail** — `update()` just overwrites `status` in place, with no record of who changed it or when. `publish()` is a separate, unrelated action: it sets `released_at` and emits `ProductVersionPublished`, but doesn't touch `status` at all.
- **`product_version`'s publish lifecycle needs a full pass against FR-02** (`Draft`/`Ready to Publish`/`Published`/`Superseded` states, immutable content hash, idempotent impact job) — this milestone only adds the event (`publish()` sets `released_at` and emits `ProductVersionPublished`, guarded so it can't fire twice via `ProductVersionAlreadyPublished`), not the real state machine. `ProductVersion.status` (`DRAFT`/`IN_REVIEW`/`APPROVED`/`ARCHIVED`) is a *different* vocabulary than the spec's publish lifecycle and the two are not reconciled yet.
- **`source`/`source_version`/`source_location`/`requirement`/`requirement_version`/`rule`/`rule_version`/`regulatory_basis_release` writes are now gated by `require_regulatory_content_writer`** (the internal role model resolved the old `require_admin` placeholder — see "Internal role model" above). Do not treat any `Source`/`SourceVersion` row as trustworthy/citable purely because writes are now properly gated — content still needs to actually go through real RA review; everything seeded by `scripts/seed_regulatory_sources.py` is `DRAFT` and explicitly marked as AI-research-derived for exactly this reason.
- **`POST /internal-role-assignments` (propose) and its two `GET`s are still gated by `require_admin`, a known, explicitly-flagged placeholder** — no "HR" actor-type exists in RBAC yet to gate the propose endpoint more precisely. The service layer's own `_require_internal_user` check is what actually stops a customer-org admin from proposing anything (see "Internal role model" above) — `require_admin` alone is not the real protection on that endpoint.
- **One real-world account currently holds both `User.is_permanent_admin` (the CEO seat) and an APPROVED `REGULATORY_KNOWLEDGE_LEAD` `InternalRoleAssignment`, self-proposed and self-decided** via `scripts/bootstrap_interim_operator.py` — not a considered dual-hat grant, an interim single-operator arrangement recorded as such in that assignment's own `rationale`/`decision_rationale` (`_INTERIM_RATIONALE`, containing the literal string "INTERIM SINGLE-OPERATOR ARRANGEMENT" — query for it if auditing who holds what and why). No identity is hardcoded anywhere in application code for this; the script takes the account's email/name/password as required CLI arguments each run. **What unblocks reassigning this properly**: (1) a second genuine internal operator (or a real HR actor-type in RBAC, closing the placeholder above) needs to exist to run the actual propose/CEO-approve flow for `REGULATORY_KNOWLEDGE_LEAD`, at which point `_supersede_prior_approved` retires this interim grant the normal way once the new one is approved; (2) permanent-admin succession has no API/script path by design (see the entry above) — moving the CEO seat off this account is a direct DB operation, deliberately outside the running application's own authority.
- **`User.is_permanent_admin` ("the CEO seat") has no succession path** — it's DB-only settable by design, with no API endpoint to transfer it to a different account, not even for the CEO's own account. Deliberate: an endpoint able to move this flag would defeat the point of it being unforgeable through the API. If real succession is ever needed, it requires a direct DB operation outside the running application, not a new authenticated endpoint that would reopen the same attack surface this flag exists to close.
- **Acting-as-a-specific-customer-organization for RegNova staff (an "RA Workbench" scope switch) is not built.** The internal role model gives RA/Senior Reviewer/etc. identity and internal-role-checking, but every existing org-scoped repository still filters strictly by `current_user.organization_id` — an RA's own tenant-zero `organization_id` never matches a customer's data under any existing query, so RA staff currently cannot see customer data through this API at all. Explicitly out of scope for this pass; needs its own audited design. This is exactly why the Finding review workflow's RA/Senior-only transitions (`reject`/`mark_not_applicable`/`reopen`/`accept_with_rationale`, and `resolve` for Critical/Major severity) are real, tested logic that's simultaneously unreachable via HTTP today — see "Finding review workflow" above.
- **Fixed: `_derive_dimension_state` no longer under-counts an open Finding once it's moved past `PROPOSED`.** Its `NON_COMPLIANT` trigger was `findings_proposed > 0` alone — `FindingRevision`s created **during that specific `AssessmentRun`** — which correctly went to zero for a Finding a fresh rerun's `propose()` deliberately declined to re-touch (its own idempotent-reuse guard, `if latest.status != PROPOSED: return None`), once the Finding review workflow made `OPEN`/`CUSTOMER_RESPONDED` real, persistent states. `_derive_dimension_state` now takes `organization_id`/`product_market_state_id` and ORs in a third, run-independent signal, `FindingService.has_open_finding(organization_id, product_market_state_id, dimension)` (backed by a new `FindingRepository.get_all_for_dimension`, filtering `Finding.dimension` directly — not a join through `RequirementVersion.dimension`, which would silently miss any Finding whose `requirement_version_id` is null, per C6's `CALCULATION_COMPONENT` allowance). Additive to the two existing signals, same shape as the `hard_gate_effect` gate fix. Verified via weaken/confirm-fail/restore and two tests in `test_assessment_run_claims.py`: `test_fresh_rerun_still_derives_non_compliant_for_an_open_finding` (the regression — an `OPEN` Finding, second run, dimension must still read `NON_COMPLIANT`) and `test_fresh_rerun_shows_compliant_once_finding_resolved` (the control — once terminal, a fresh rerun correctly reads `COMPLIANT` again, proving the check tracks current status, not "was a Finding ever proposed here").
- **⚠ Named, deferred limitation: this fix only helps a FRESH (non-reused) dimension computation — reuse can still serve a stale `DimensionAssessment.state`, in either direction.** `MarketReadinessService._resolve_dimension`'s key-absent path returns a reused `DimensionAssessment` row unchanged whenever pins match; `_derive_dimension_state` (and therefore the fix above) simply never runs on that path. Two distinct staleness directions follow from the same root cause — `DimensionAssessment.state`, once written, is never invalidated by a later Finding transition:
  - **Under-blocking**: a Finding sits `OPEN`, but if its dimension gets *reused* instead of freshly recomputed, whatever state was stored at the *original* run persists — the fix above never fires on this path.
  - **Over-blocking**: a Finding gets `RESOLVED` after its dimension was computed as `NON_COMPLIANT`; nothing re-triggers `_derive_dimension_state` on resolution, so a later reused `DimensionAssessment` keeps showing `NON_COMPLIANT` for an issue that's actually closed.

  Closing this needs a reuse-eligibility check analogous to the facts-hash one (`DimensionAssessment.submitted_facts_hash` — see "Market readiness" above): `get_latest_reusable` would need to additionally check whether any Finding for that dimension has transitioned *since* the candidate row was created (e.g. against `FindingRevision.created_at`), and force a rerun if so. Not implemented — deliberately deferred, same as the facts-hash fix's own explicitly-left-open key-absent gap.
- **⚠ Named, open question: dimension-level `NON_COMPLIANT` is severity-blind; the gate is not.** `findings_proposed > 0` and `has_open_finding` both treat *any* open Finding as equally disqualifying, regardless of severity or `hard_gate_effect` — unlike `MarketReadinessService._compute_gate`, which (since the `hard_gate_effect` fix, see "Market readiness" above) distinguishes Critical/hard-gated findings from Moderate/Minor/Informational ones at the gate level. Kept consistent with `findings_proposed`'s own pre-existing severity-blindness rather than introduced as new inconsistency — but whether dimension-level state *should* eventually become severity/hard-gate-aware the way the gate now is, is a real, undecided question, not something this fix resolved either way.
- **⚠ Named, deferred follow-up: `_run_documents_dimension`'s `consistency_checks[]` pool has the same structural risk `NO_SUBJECTS_RESOLVED` was just fixed for on the subject-list dimensions, not yet addressed.** `consistency_rules` (active rules whose `RequirementVersion.subject_kind == CONSISTENCY_CHECK`) can be non-empty while the caller's `dimension_facts.get("consistency_checks", [])` is empty — zero `StepRun`s get created for that pool, silently indistinguishable from "no consistency-check rules exist." The per-document pool doesn't share this risk (its subject list, `document_types`, is derived from `document_rules` itself, not from caller input — a required `document_type` the caller never submitted is still evaluated as empty facts). Deliberately not folded into the `NO_SUBJECTS_RESOLVED` fix: Documents' checklist is regulatory-basis-driven rather than caller-driven, so the right fix shape (likely: treat `consistency_rules` non-empty + zero submitted `consistency_checks` the same way, but scoped to that one pool rather than the whole dimension) needs its own reasoning pass, not an unreasoned extension of a fix designed for the other branch.
- **`source_version`'s draft→review→verified→active→superseded→archived lifecycle has no dedicated transition methods or audit trail**, mirroring `product_version`'s same gap — see the "Regulatory content" section above.
- **`assessment_run` executes entirely synchronously within the request — no job queue exists yet.** Confirmed acceptable for the Claims-only vertical slice; Label has now landed as a second dimension (technically firing one half of the originally-logged revisit trigger), but each `AssessmentRun` still only requests one dimension at a time and rule/subject counts remain small in tests — not yet actually causing timeouts. Keep watching this: once a single request drives multiple dimensions together, or a real product's claim/label-field set grows past a handful of items, move to the outbox/worker pattern `audit` already uses.
- **`RequirementResult.outcome` accepts `CONFLICT` but the engine never produces it** — detecting genuine multi-rule applicability disagreement isn't built; each `APPLICABILITY` rule evaluates independently. See "Assessment engine" above.
- **`FindingRevision`'s Recommendation field group (`action_type`/`suggested_value`/`resolution_criteria`/owner/due date) is never populated** — `RuleVersion` has nowhere to source a structured action template from yet; C7's "NO FREE-TEXT-ONLY FINDINGS" rule is only partially satisfied until that's built. See "Assessment engine" above.
- **The engine's normalize-function registry (`lowercase`/`strip`/`collapse_whitespace`) is a tiny placeholder**, not the real "approved normalization functions" registry C6 gestures at and that CLAUDE.md already flags as undefined anywhere in the spec.
- **`DEFAULT_MIN_CONFIDENCE` (0.5, D5.1/Appendix 4's own spec-supplied default) is hardcoded in `app/engine/condition_evaluator.py`, not sourced from `RegulatoryBasisRelease.configuration`** — B5.2's own precedent is that regulatory thresholds are versioned config, not hardcoded, but the engine is a pure function with no release context threaded in yet. See "Assessment engine" above.
- **Documents (FR-08) has no real `Evidence`/`Document` model behind it** — `documents[]`/`consistency_checks[]` input facts are entirely synthetic, standing in for FR-04's real upload/malware-scan/OCR/extraction pipeline (unbuilt, C8 territory), the same way Claims/Label's facts stand in for their own unbuilt extraction layers. Specifically deferred: one Evidence object satisfying multiple requirements/products (FR-08's many-to-many evidence linking — this pass evaluates one requirement per checklist item, no reuse across requirements), and AC-FR-08-04's targeted re-evaluation on document-version change (needs real Document/Document Version identity and change-impact propagation, C11 territory). See "Assessment engine" above.
- **"Expiry reminders... event-driven at configurable intervals" (FR-08) is not built as a notification/scheduling mechanism** — only the point-in-time consequence (today's `days_until_expiry` band determining Expiring-Soon/Expired Finding rules) is implemented. Nothing proactively watches a calendar and fires alerts; that's a recurring-job concern this synchronous, request-only engine doesn't have infrastructure for yet (see the sync-only execution note above).
- **"Detected claims" on Label (FR-06) does not cross-reference Claims Review's (FR-07) own results** — confirmed out of scope for this pass; each dimension's `StepRun`s are independent within one `AssessmentRun`. Genuine cross-dimension referencing is C11/C13 territory.
- **G4 (Ready for Registration) and G5 (Authority Confirmed) are permanently unreachable** — no Approval model exists (G4) and no Execution/Authority Event data exists (G5); whatever would otherwise be G4 is deliberately capped at G3 rather than silently overclaiming readiness. Revisit once Approval and Execution/Authority Event entities (C2) are built. See "Market readiness" above.
- **`StateSnapshot.configuration_hash` is always `null`** — only one hardcoded engine constant exists to hash (`DEFAULT_MIN_CONFIDENCE`), not yet release-scoped configuration; hollow until that threshold moves into `RegulatoryBasisRelease.configuration` (see the `DEFAULT_MIN_CONFIDENCE` entry above, which this depends on).
- **A `RequirementVersion` enforced purely via `FINDING_PROPOSAL` rules contributes no weight to its dimension's B5.2 progress score** — that output type never writes a `RequirementResult` row, only a `Finding`, so `MarketReadinessService._dimension_score` never sees it. A dimension enforced entirely this way would show 0 applicable requirements and fall back to a state-derived score instead of a weighted one.
- **Market Readiness preflight does not check "required intake fields"** — no such checklist is modeled anywhere in this codebase (Product/ProductVersion has no concept of it). Deferred rather than inventing a synthetic field list. See "Market readiness" above.
- **⚠ Market Readiness reuse can still serve a WRONG gate on the key-absent path: nothing submitted this run means nothing to compare against.** `DimensionAssessment.submitted_facts_hash` (see "Market readiness" above) closes the case where a caller *resupplies* a dimension's facts — identical resupply now reuses safely, genuinely different resupply always reruns. It does **not** close the case where a caller *omits* a dimension's key entirely: `get_latest_reusable`'s key-absent path still trusts `(product_version_id, regulatory_basis_release_id)` pins alone, because there is nothing submitted that run to hash and compare — this is not a gap in the hash's design, it's an information-theoretic limit of the current architecture. Concretely: if real-world facts change (e.g. a claim's wording is corrected in a UI that doesn't touch `ProductVersion`) and the caller doesn't know or doesn't remember to explicitly resupply that dimension's key on a later run, `DimensionAssessment` reuse will silently serve the **old** assessment — computed from the old facts — with no error or warning. **Root cause, unchanged by this fix**: no dimension's input facts are derived from `ProductVersion`'s own stored data — Claims/Label/Documents facts are all caller-supplied JSON per request, disconnected from anything persisted, so there is no ground truth this codebase could check an omitted submission against even in principle. **What could actually close this** — neither is built: (1) a protocol change, requiring every run to either resupply a dimension's facts or explicitly assert "no change" for it, so silence is never ambiguous with "verified unchanged"; or (2) an architecture change, deriving dimension facts from persisted product/document data (the Document/Evidence model scoped separately) instead of ephemeral per-request JSON, so there'd be real stored state to diff against regardless of what a given request happens to submit. Hashing submitted facts was the fix available within the current architecture; it is not a substitute for either of these.
